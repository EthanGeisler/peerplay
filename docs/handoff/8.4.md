# 8.4 — Schema: Add relay/signature fields

## What was built

Added database schema support for relay federation:

1. **Listing model** — two new optional fields:
   - `creatorPublicKey` (`creator_public_key`) — secp256k1 pubkey (64-char hex) of the listing creator
   - `signature` — Schnorr signature over listing data

2. **Relay model** — tracks known relay servers for federation:
   - `url` (unique), `name`, `lastSyncAt`, `status`, `trustedByDefault`

3. **FederatedListing model** — stores listings imported from external relays:
   - Separate from local `Listing` table (no FK to developers/users)
   - Unique on `(relayUrl, remoteId)` — prevents duplicate imports
   - Indexed on `slug` and `creatorPubkey` for search/filtering
   - Includes `contentType`, `metadata`, `priceCents`, `coverImageUrl`

## Key decisions

- **FederatedListing is separate from Listing**: Federated listings don't have a local developer, so they can't share the same table without making `developerId` nullable (which would break existing constraints). A separate table keeps the local listing model clean.
- **creatorPublicKey on Listing is optional**: Existing listings predate the signing system. They'll have null values until creators sign them.
- **Relay.status is a string, not an enum**: Allows flexible status values (active, inactive, banned) without requiring a migration for each new status.

## How it works

- Migration `20260319024011_add_relay_federation_models` adds the columns and tables
- Existing listings are unaffected (new fields default to null)
- The `relays` table will be populated when federation endpoints are built (sub-task 8.5)
- The `federated_listings` table will be populated when the relay subscriber imports listings

## Gotchas

- The `games` table name is still used in the DB (from the Phase 7 `@@map` rename) — the migration correctly targets `games` for the ALTER TABLE
- `FederatedListing` uses `ContentType` enum which maps to `content_type` in the DB — shared with `Listing`
