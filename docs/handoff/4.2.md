# Sub-task 4.2 — Profile Events (Kind 0)

## What was built
- **`server/packages/relay/src/routes.ts`** (MODIFIED) — Added two new REST endpoints:
  - `PUT /api/profiles/me` (authenticated) — set/update user profile via kind 0 event
  - `GET /api/profiles/:pubkey` (public) — get profile data from latest kind 0 event
- **`server/packages/shared/src/events.ts`** (MODIFIED) — Extended replaceable event semantics to properly handle NIP-01 regular replaceable kinds (0, 3, 10000-19999), not just parameterized replaceable kinds (30000-39999)
- **`server/packages/shared/src/eventStore.ts`** (MODIFIED) — Updated comments to reflect the broader replaceable kind coverage
- **`server/packages/shared/src/index.ts`** (MODIFIED) — Added exports for `isRegularReplaceableKind` and `isParameterizedReplaceableKind`

## Key decisions made during implementation

- **Extended `isReplaceableKind` instead of handling at the route level.** The eventStore's `storeEvent` already has replaceable semantics that handle the "only one event per pubkey+kind+dTag" constraint. Kind 0 is a regular replaceable event per NIP-01 (like kind 3 follow lists). Rather than implementing ad-hoc replacement logic in the profile route, I extended the shared `isReplaceableKind()` function to recognize all NIP-01 replaceable kinds (0, 3, 10000-19999). This means the eventStore now correctly handles replaceability for kind 0 and kind 3 events automatically.

- **Three new exported functions in events.ts:**
  - `isRegularReplaceableKind(kind)` — returns true for kinds 0, 3, 10000-19999
  - `isParameterizedReplaceableKind(kind)` — returns true for kinds 30000-39999 (was previously `isReplaceableKind`)
  - `isReplaceableKind(kind)` — returns true for either type (updated, backward-compatible)

- **`normalizeDTag` updated:** Regular replaceable kinds always get `dTag = ""` (they don't use parameterized d-tags, but still need a non-null dTag for the `@@unique([pubkey, kind, dTag])` constraint). This is correct per NIP-01.

- **No Zod schema for profile input.** The profile body is simple (`{ name?, about?, picture? }` — all optional strings), and inline validation matches the existing pattern in sign-and-publish. Adding a Zod schema would be overkill here.

- **Migration from displayName:** On the first `PUT /profiles/me` call (when no kind 0 event exists yet), the `name` field is seeded from the user's existing `displayName` in the User table. If the caller explicitly provides `name`, it takes precedence. On subsequent updates, no auto-seeding occurs.

## How it works

### PUT /api/profiles/me (authenticated)
1. Validates input (name, about, picture — all optional strings)
2. Loads user's `nostrPubkey` and `displayName` from DB
3. Queries for existing kind 0 events by this pubkey to detect first profile creation
4. Builds profile content JSON:
   - If `name` is provided, uses it
   - If `name` is not provided AND this is the first profile AND user has a `displayName`, seeds from `displayName`
   - `about` and `picture` included if provided
5. Signs a kind 0 event via `signEventForUser` with `tags: []` and `content: JSON.stringify(profileContent)`
6. Stores via `storeEvent` (replaceable semantics ensure only one kind 0 per pubkey)
7. Fans out to WS subscribers, federates outbound
8. Returns the profile content object

### GET /api/profiles/:pubkey (public)
1. Validates pubkey format (64-char hex)
2. Queries latest kind 0 event for that pubkey (limit 1, ordered by created_at desc)
3. Returns 404 if no profile event exists
4. Parses event content JSON, returns `{ pubkey, ...profileData, created_at }`

### Replaceable event semantics for kind 0
The `storeEvent` function in eventStore.ts now recognizes kind 0 as replaceable:
- `isReplaceableKind(0)` returns `true`
- `normalizeDTag(0, [])` returns `""` (regular replaceable — no d-tag parameterization)
- eventStore uses the `@@unique([pubkey, kind, dTag])` constraint to find and replace existing events
- If a newer kind 0 event arrives for the same pubkey, it replaces the old one
- Only one kind 0 event per pubkey exists in the database at any time

## Gotchas and surprises

- **The original `isReplaceableKind` only handled kinds 30000-39999.** This was fine for Phase 2 (game listings/versions), but kind 0 (profile) and kind 3 (follow list) are NIP-01 "regular replaceable" events that need the same treatment. Without this fix, multiple kind 0 events could accumulate for the same pubkey.

- **The dTag for regular replaceable kinds must be `""` not `null`.** Prisma's `@@unique` constraint treats NULL as distinct values (PostgreSQL behavior), so two events with `dTag: null` would both be insertable. Setting `dTag: ""` for regular replaceable kinds ensures the unique constraint correctly prevents duplicates.

## How to use / test

### Set profile
```bash
curl -X PUT https://boilerdeck.com/api/profiles/me \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"name":"Alice","about":"Game developer","picture":"https://example.com/avatar.jpg"}'
```
Response: `{"name":"Alice","about":"Game developer","picture":"https://example.com/avatar.jpg"}`

### Get profile
```bash
curl https://boilerdeck.com/api/profiles/<64-char-hex-pubkey>
```
Response: `{"pubkey":"...","name":"Alice","about":"Game developer","picture":"https://example.com/avatar.jpg","created_at":1710720000}`

### Verify replaceable semantics
Call PUT twice — the second call replaces the first. Query the events table:
```bash
curl "https://boilerdeck.com/api/events?kinds=0&authors=<pubkey>"
```
Should return exactly one event.

## What the next sub-task needs to know

- **4.3 (Review events)** can follow the same pattern: use `signEventForUser` to create the event, `storeEvent` to store it, `fanOutEvent` + `federateOutbound` for distribution.
- **Kind 3 (follow list) events in 4.6** will automatically get replaceable semantics thanks to the `isRegularReplaceableKind` change. No additional work needed in the eventStore.
- **Profile data is not materialized to the User table.** The profile lives entirely as a kind 0 event. If future tasks need profile data denormalized into the User table, a materializer should be added.
- **The `isReplaceableKind` change is backward-compatible** — it only adds more kinds to the replaceable set. Existing kind 30000-39999 behavior is unchanged.
