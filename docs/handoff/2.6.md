# Sub-task 2.6 — Wrap game updates and publishing in event signing

## What was built
- **`server/packages/catalog/src/routes.ts`** (MODIFIED) — PUT `/developer/games/:id`, PATCH `publish`, and PATCH `unpublish` handlers now sign kind 30001 events after the DB operation completes

## Key decisions made during implementation
- **Status tag included.** All three handlers add a `["status", gameStatus]` tag to the event. For publish it's `"PUBLISHED"`, for unpublish it's `"DRAFT"`, for update it's whatever the current status is.
- **Replaceable semantics via same d tag.** All events use `["d", game.slug]` which means they replace the previous event for the same game (same pubkey + kind + dTag).
- **DUPLICATE check before game.update.** The `storeEvent()` return value is checked — if it returns `"DUPLICATE"` (same-second timestamps), the `db.game.update` call is skipped. This prevents FK constraint violations when the replaceable event store doesn't actually store the new event (because the existing one has a newer or equal `created_at`).

## How it works

```
PUT /api/developer/games/:id { title?, description?, priceCents? }
  -> updateGame(gameId, developerId, input)
  -> signEventForUser(userId, { kind: 30001, tags: [d, t, status], content })
  -> storeEvent(event) -> if STORED or REPLACED:
     -> db.game.update({ eventId: event.id })
  -> res.json(game)

PATCH /api/developer/games/:id/publish
  -> publishGame(gameId, developerId)
  -> signEventForUser -> storeEvent -> db.game.update (same pattern)
  -> res.json(game)

PATCH /api/developer/games/:id/unpublish
  -> unpublishGame(gameId, developerId)
  -> signEventForUser -> storeEvent -> db.game.update (same pattern)
  -> res.json(game)
```

## Gotchas and surprises
- **FK violation on rapid operations.** When two events are created in the same second (same `created_at` Unix timestamp), the replaceable event store returns "DUPLICATE" without storing the new event. If we then try to set `Game.eventId` to the new event's id, it violates the FK constraint because that id doesn't exist in the events table. Fixed by checking `storeEvent()` return value.
- **CASCADE on event id changes.** The `storeReplaceableEvent` function updates the existing event row's `id` to the new event's `id`. PostgreSQL's `ON UPDATE CASCADE` on the FK propagates this change to `games.event_id`. This means the game's eventId can change "behind the scenes" via CASCADE even before our explicit `db.game.update` call.

## What the next sub-task needs to know
- 2.7 uses the same pattern but with kind 30002 for game versions. The d tag pattern is `slug:version` instead of just `slug`.
- The `result !== "DUPLICATE"` guard should be used for any event signing that follows the replaceable pattern.
