# Sub-task 2.4 — Server-side signing service

## What was built
- **`server/packages/auth/src/signing.ts`** (NEW) — `signEventForUser(userId, params)` signs NIP-01 events for custodial users
- **`server/packages/auth/src/index.ts`** — re-exports `signEventForUser`

## Key decisions made during implementation
- **`decryptFromCache` is local to signing.ts.** The `encryptForCache` function lives in `service.ts` (from Phase 1.5). The inverse decrypt is only needed here, so it stays co-located with the signing logic rather than being extracted to a shared util.
- **Three distinct error messages.** Self-custody ("sign client-side"), no Redis key ("session expired, log in again"), and decrypt failure ("session expired, log in again") all throw `UnauthorizedError` but with different messages. This helps debugging without leaking internals.
- **`created_at` set at signing time.** Uses `Math.floor(Date.now() / 1000)` — the server's clock is authoritative for custodial signing. This means concurrent signs get the same timestamp, but different content/tags produce different event IDs.

## How it works

```typescript
const event = await signEventForUser(userId, {
  kind: 30001,
  tags: [["d", "game-slug"]],
  content: '{"title":"My Game"}',
});
// Returns: { id, pubkey, created_at, kind, tags, content, sig }
```

Flow:
1. Load user from DB → get `nostrPubkey` and `custodyMode`
2. If `SELF_CUSTODY` → throw (must sign client-side)
3. Load `signing_key:{userId}` from Redis
4. If missing → throw (session expired)
5. Decrypt with `SIGNING_CACHE_KEY` env var (AES-256-GCM)
6. If decrypt fails → throw (key rotated or corrupted)
7. Call `createEvent()` from shared → returns signed event

## Gotchas and surprises
- **Cache format is `nonce:tag:ciphertext`** (not `v1:salt:nonce:tag:ciphertext`). The Redis cache encryption uses a simpler format than the DB encryption because there's no need for scrypt key derivation — the key is already in memory as `SIGNING_CACHE_KEY`.
- **Concurrent signing works because** Redis reads are independent and the private key is deterministic — same key signs different content, producing different events.

## What the next sub-task needs to know
- Sub-tasks 2.5-2.7 should call `signEventForUser(userId, { kind, tags, content })` after game creation/update/version upload.
- The function returns a `SignedEvent` — pass it to `storeEvent()` from shared to persist.
- If signing fails (self-custody, expired session), **don't block the game operation** — create the game/version with `eventId: null` and let the event be created later.
- The caller needs the `userId` from the authenticated request (`req.user.sub` via JWT).
