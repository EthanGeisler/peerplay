# Sub-task 3.2 — Prisma Schema: Events Table + User Keypair

## What was built
- **`server/prisma/schema.prisma`** (MODIFIED) — Added compound `@@index([kind, createdAt])` to Event model
- **`server/prisma/migrations/20260318120000_add_events_compound_index/migration.sql`** (NEW) — Migration SQL

## Key decisions made during implementation
- **Only a compound index was needed.** The Event model (from 2.1) and User keypair fields (from 1.3) were already complete. The only missing piece was the `[kind, createdAt]` compound index needed for efficient `queryEvents` filtering by kind with time-ordered results.
- **Same migration approach as 2.1.** Wrote SQL directly to migration directory, applied with `prisma migrate deploy` (not `migrate dev`, which doesn't work in non-interactive shells).

## How it works
The compound index `events_kind_created_at_unix_idx` on `(kind, created_at_unix)` optimizes the most common relay query pattern: "give me the newest events of kind X." PostgreSQL can satisfy this with a single index scan instead of scanning the kind index then sorting by timestamp.

## Gotchas and surprises
- **Index column name is `created_at_unix`**, not `created_at`. The Prisma model uses `createdAt` (camelCase) but `@map("created_at_unix")` maps it to the actual column name in PostgreSQL. The migration SQL must use the mapped name.

## What the next sub-task needs to know
- Schema is stable. No further migrations needed for 3.3.
- The existing indexes are: `kind`, `pubkey`, `createdAt`, `[kind, createdAt]`, and unique on `[pubkey, kind, dTag]`.
