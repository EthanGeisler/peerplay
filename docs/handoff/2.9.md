# Sub-task 2.9 — Event materialization layer

## What was built
- **`server/packages/shared/src/eventMaterializer.ts`** (NEW) — `materializeEvent()` converts NIP-01 events into legacy DB rows
- **`server/packages/shared/src/eventRoutes.ts`** (MODIFIED) — POST /api/events calls materializeEvent() after storeEvent()
- **`server/packages/shared/src/index.ts`** (MODIFIED) — Exports materializeEvent

## How it works

```
materializeEvent(event) → switch on event.kind:
  30001 (Game Listing):
    1. Extract slug from d tag
    2. Parse content JSON for title, description, priceCents
    3. Look up developer via pubkey (User.nostrPubkey → Developer)
    4. Check slug collision (different developer = SKIPPED)
    5. Extract status tag (PUBLISHED or DRAFT)
    6. db.game.upsert({ where: { slug }, create: {...}, update: {...} })

  30002 (Game Version):
    1. Extract d tag (format: "slug:version")
    2. Parse content JSON for version, fileSizeBytes, infoHash
    3. Find game by slug, verify developer ownership via pubkey
    4. db.gameVersion.upsert({ where: { gameId_version }, ... })

  Other kinds → "NO_OP"
```

## Key decisions
- **Not called from internal signing flow.** The 2.5-2.7 handlers (createGame, updateGame, etc.) already write the correct DB state directly. Materializing their own events would be redundant and could cause issues with field overwriting. Materialization is for externally-submitted events via POST /api/events.
- **Returns string status, not throws.** Invalid events (malformed JSON, missing fields, wrong developer, non-existent game) return "SKIPPED" instead of throwing. The materialization is non-fatal from the POST /api/events perspective.
- **Slug collision protection.** If a game slug already exists and belongs to a different developer, materialization is skipped. No error, no overwrite.
- **Out-of-order events skipped.** If a version event arrives before its game event, it's skipped (game.findUnique returns null). No queueing mechanism — the event is stored but not materialized until re-processed.

## Gotchas
- **Game.eventId set by materialization.** The upsert sets `eventId: event.id`, which links the game to the event. If this conflicts with the CASCADE from replaceable event storage, it could cause issues. In practice, this only matters for externally-submitted events since internal flow sets eventId explicitly.
- **GameVersion status set to READY.** Materialized versions are created with status "READY" since the event represents a completed upload. Real uploads go through PROCESSING → READY via uploadAndProcessVersion.
