# Sub-task 1.4 — Generate keypair on registration (custodial + self-custody paths)

## What was built
- **`server/packages/auth/src/service.ts`** — updated `register()` to generate a Nostr keypair (custodial) or accept a client-provided pubkey (self-custody)
- **`server/packages/auth/src/schemas.ts`** — added optional `pubkey` field to `registerSchema`

## Key decisions made during implementation
- **Create user first, then update with keypair data.** The keypair generation (especially scrypt-based encryption) is CPU-intensive. By creating the user first and updating after, we keep the user creation fast and avoid holding the DB transaction open during crypto operations. If keypair generation fails after user creation, the user exists without a keypair — the lazy migration in 1.6 will catch this on first login.
- **Spread mnemonic conditionally.** Used `...(mnemonic ? { mnemonic } : {})` to avoid including the `mnemonic` key at all in self-custody responses, rather than setting it to `null`/`undefined`.
- **String literals for CustodyMode.** Used `"CUSTODIAL"` / `"SELF_CUSTODY"` string literals instead of importing the Prisma enum — both work with Prisma and the string form avoids an extra import.

## How it works

### Custodial registration (default)
```
POST /api/auth/register { email, password, displayName }
  → db.user.create() (email, passwordHash, displayName)
  → generateKeypair() → { mnemonic, publicKey, privateKey }
  → encryptPrivateKey(privateKey, password) → encrypted nsec
  → encryptMnemonic(mnemonic, password) → encrypted mnemonic
  → db.user.update() with nostrPubkey, encryptedNsec, encryptedMnemonic, custodyMode=CUSTODIAL
  → return { user: { ...existing, nostrPubkey }, accessToken, refreshToken, mnemonic }
```

### Self-custody registration
```
POST /api/auth/register { email, password, displayName, pubkey: "64-char-hex" }
  → db.user.create() (email, passwordHash, displayName)
  → db.user.update() with nostrPubkey=pubkey, encryptedNsec=null, encryptedMnemonic=null, custodyMode=SELF_CUSTODY
  → return { user: { ...existing, nostrPubkey }, accessToken, refreshToken }
  (no mnemonic in response)
```

### Schema change
```ts
// schemas.ts
registerSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
  displayName: z.string().min(2).max(50),
  pubkey: z.string().length(64).regex(/^[0-9a-f]+$/).optional(),
})
```

## Gotchas and surprises
- **scrypt is synchronous and CPU-intensive.** `encryptPrivateKey` and `encryptMnemonic` both call `scryptSync` with N=32768. This blocks the event loop for ~100-200ms per call. On registration this happens twice (encrypting privkey + mnemonic). For a high-traffic deployment this could be a bottleneck — consider moving to `scrypt` (async) in the future.
- **Pubkey uniqueness constraint.** The `nostr_pubkey` column has a unique index. If someone tries to register with a `pubkey` that already exists in the DB, Prisma throws a P2002 error. The error handler will return a 500 — a future improvement could catch P2002 and return a 409 Conflict.

## How to use / test
```bash
# Custodial registration
curl -s -X POST http://localhost:3001/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"testpass123","displayName":"Test User"}' | jq .

# Self-custody registration (provide your own pubkey)
curl -s -X POST http://localhost:3001/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"test2@example.com","password":"testpass123","displayName":"Test User 2","pubkey":"17162c921dc4d2518f9a101db33695df1afb56ab82f5ff3e5da6eec3ca5cd917"}' | jq .
```
