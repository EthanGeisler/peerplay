# Sub-task 1.7 — Challenge-based login (sovereign mode)

## What was built
- **`server/packages/auth/src/service.ts`** — added `generateChallenge()` and `loginWithPubkey()` functions
- **`server/packages/auth/src/routes.ts`** — added `GET /api/auth/challenge` (rate-limited) and `POST /api/auth/login/pubkey`
- **`server/packages/auth/src/schemas.ts`** — added `pubkeyLoginSchema` (validates pubkey, challenge, signature)
- **`express-rate-limit`** — installed as dependency

## Key decisions made during implementation
- **Challenge is SHA-256 hashed before verification.** The client signs `SHA-256(challenge_bytes)`, not the raw challenge hex string. This matches how Nostr event signing works (sign the hash, not the content).
- **Challenge deleted before signature verification.** One-time use enforced immediately — even a valid signature can't reuse a challenge.
- **Dynamic import for `@noble/hashes`.** Used `await import()` for the SHA-256 import inside `loginWithPubkey()` to avoid potential ESM/CJS issues at module load time.
- **Rate limiter on challenge only.** The pubkey login endpoint doesn't need its own rate limit — each attempt consumes a challenge, and challenges are already rate-limited.
- **Error response format matches convention.** Rate limiter returns `{ error: { code, message } }` to match the app's standard error shape.

## How it works

### Challenge flow
```
GET /api/auth/challenge
  → rate limit: 10 req/IP/min
  → generate 32 random bytes → 64-char hex
  → redis.set("challenge:{hex}", "1", "EX", 300)  // 5 min TTL
  → return { challenge, expiresAt }
```

### Pubkey login flow
```
POST /api/auth/login/pubkey { pubkey, challenge, signature }
  → verify challenge exists in Redis (not expired)
  → delete challenge from Redis (one-time use)
  → SHA-256(challenge_bytes) → messageHash
  → schnorrVerify(pubkey, messageHash, signature)
  → if invalid → 401
  → db.user.findUnique({ nostrPubkey: pubkey })
  → if not found → 404
  → issue JWT (with pubkey claim) + refresh token
  → return { user, accessToken, refreshToken }
```

### Schema
```ts
pubkeyLoginSchema = z.object({
  pubkey: z.string().length(64).regex(/^[0-9a-f]+$/),     // 32-byte x-only pubkey
  challenge: z.string().length(64).regex(/^[0-9a-f]+$/),  // 32-byte challenge
  signature: z.string().length(128).regex(/^[0-9a-f]+$/), // 64-byte Schnorr sig
})
```

## Gotchas and surprises
- **Challenge is bytes, not string.** The challenge hex is converted to bytes before hashing: `SHA-256(Buffer.from(challenge, "hex"))`. If the client hashes the hex string instead of bytes, verification will fail.
- **No signing key cache for pubkey login.** Self-custody users don't have `encryptedNsec` on the server, so there's nothing to cache in Redis. The `signing_key:{userId}` key won't exist for these users.
- **`express-rate-limit` uses in-memory store by default.** Fine for single-server deployment. If we scale to multiple servers, we'd need `rate-limit-redis`.
