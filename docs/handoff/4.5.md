## Key decisions made during implementation

- **Electron local signing approach.** The main process IPC handler `events:sign-and-publish-review` handles the full flow: gets the private key (self-custody key from OS-encrypted store, or server-fetched cached key), builds the NIP-01 event, signs with Schnorr, and publishes via the relay WebSocket. This keeps crypto operations in the main process (Node.js environment) where `@noble/curves` works best.

- **Key resolution order.** The Electron client tries: (1) cached relay keys from store (`relayPrivkey`/`relayPubkey`), (2) self-custody key decrypted via `safeStorage`. If neither is available, throws `NO_KEY` which triggers REST fallback.

- **REST fallback.** If local signing fails for any reason (no key, relay not connected, signing error), the Electron client falls back to `POST /api/games/:slug/reviews` — same as the web storefront. This ensures reviews always work.

- **Relay auto-connect on submit.** The client ReviewForm checks relay connection status and attempts to connect before publishing. The relay URL is derived from the API base URL.

- **Key caching via renderer.** The renderer fetches keys via `GET /api/relay/me/keys` (using authenticated apiFetch) and caches them to the main process store via `events:cache-relay-keys` IPC. This avoids duplicating auth token handling in the main process.

- **Visibility rules via review list check.** Rather than adding a new API endpoint, the "has already reviewed" check loads the existing reviews list and compares pubkeys. This is efficient since reviews are bounded (one per user per game) and the list is already fetched by ReviewSection.

## How it works

### Web ReviewForm
1. Star selector (1-5, hover preview), title input, body textarea, submit button
2. Client-side validation: rating required, title required, body required
3. Submits via `POST /api/games/:slug/reviews` with `{ rating, title, body }`
4. On success, shows confirmation message and calls `onReviewSubmitted` callback
5. Parent (GameDetail) increments `reviewRefreshKey` which triggers ReviewSection re-fetch

### Electron ReviewForm — Local Signing Flow
1. Same UI as web
2. On submit, calls `submitViaRelay()`:
   a. Fetches user's private key via `GET /api/relay/me/keys` and caches via `events:cache-relay-keys` IPC
   b. Checks relay connection status, auto-connects if needed
   c. Calls `events:sign-and-publish-review` IPC which:
      - Retrieves privkey from store (cached relay key or self-custody key)
      - Builds kind 31337 event with content `{ rating, title, body }` and tags `[["d", slug]]`
      - Computes NIP-01 event ID: `SHA-256(JSON.stringify([0, pubkey, created_at, kind, tags, content]))`
      - Signs with Schnorr via `@noble/curves`
      - Publishes via `relayManager.publish()` (WebSocket)
   d. Returns signed event to renderer
3. If any step fails, falls back to REST POST (same as web)

### Visibility Rules
- ReviewForm only rendered if ALL conditions are met:
  1. `user` is not null (logged in)
  2. `owned` is true (user has ACTIVE license for this game)
  3. `hasReviewed` is false (no review with user's pubkey in the reviews list)

### Review Refresh
- ReviewSection accepts `refreshKey` prop — when it changes, the component resets and re-fetches from offset 0
- GameDetail tracks `reviewRefreshKey` state, increments on successful submission
- The "has reviewed" check also re-runs when `reviewRefreshKey` changes

## Gotchas and surprises

- **User pubkey field inconsistency.** The `ApiUser` type has both `pubkey` and `nostrPubkey` fields. The check uses `user.pubkey || user.nostrPubkey` to handle both.

- **Relay connection timing.** After calling `relay.connect()`, there's a 1-second delay before checking status. WebSocket connection isn't instant, and there's no promise-based "connected" event from the relay manager.

- **Self-custody vs custodial keys.** Self-custody users get `privkey: null` from `GET /api/relay/me/keys`. The main process handler falls through to check the OS-encrypted self-custody key. Custodial users get the privkey from the server and cache it locally.
