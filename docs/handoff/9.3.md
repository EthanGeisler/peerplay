# 9.3 — Server Locker API (Upload & Index)

## Summary

Created the `@boilerdeck/locker` package in the server monorepo with four authenticated endpoints: file upload, entry listing, entry deletion, and torrent file download. The package follows existing monorepo patterns (ESM, Express router, JWT auth middleware, try/catch + next(err), Transmission RPC integration). All endpoints encrypt/decrypt locker metadata using NIP-44 (from Phase 9.2) and publish/query Nostr events (kind 30078) via the shared event store.

## What Changed

### New Package: `server/packages/locker/`

#### `src/config.ts` — Locker-specific configuration
- `getLockerConfig()` reads three env vars with defaults:
  - `LOCKER_DIR` — file storage root (default: `./data/locker`)
  - `LOCKER_MAX_FILE_SIZE` — multer file size limit in bytes (default: 5 GB)
  - `LOCKER_QUOTA_GB` — per-user storage quota (default: 50 GB)
- Separate from shared `config.ts` to avoid requiring locker env vars globally

#### `src/storage.ts` — File storage abstraction
- Directory helpers: `getUserDir`, `getEntryDir`, `getFilePath`, `getTorrentPath`
- `saveFile()` — moves multer temp file to `LOCKER_DIR/<userId>/<entryId>/<filename>`
- `saveTorrentFile()` — writes .torrent buffer to entry directory
- `readTorrentFile()` — reads .torrent file from disk
- `computeFileHash()` — streams file through SHA-256 (crypto.createHash)
- `getUserStorageBytes()` — recursive directory size calculation for quota checks
- `markForCleanup()` — creates `.deleted` marker file (actual deletion deferred to 9.10 cron)
- `entryExists()` — checks if entry directory exists

#### `src/service.ts` — Business logic
- **`uploadFile()`** — full upload pipeline:
  1. Quota check (filesystem-based, Prisma tracking added in 9.4)
  2. Save file to `LOCKER_DIR/<userId>/<entryId>/`
  3. Compute SHA-256
  4. Detect MIME type via `mime-types` package
  5. Create torrent via `@boilerdeck/torrent` `createTorrent()`
  6. Save .torrent file
  7. Add to Transmission RPC (non-blocking, non-fatal)
  8. Build `LockerEntry` JSON (from Phase 9.1 types)
  9. Encrypt with NIP-44 to user's own pubkey
  10. Sign & publish kind 30078 event via `signEventForUser()` + `storeEvent()`
  11. Return `{ entryId, infoHash, eventId }`
- **`listEntries()`** — queries event store for user's kind 30078 events, decrypts each with NIP-44, returns `{ entries, quota: { used, max } }`
- **`deleteEntry()`** — finds event by d-tag, publishes kind 5 (NIP-09) deletion event, removes torrent from Transmission (non-fatal), marks files for cleanup
- **`getTorrentFile()`** — verifies ownership via event query, returns .torrent buffer
- Private helpers:
  - `getUserPrivkeyHex()` — decrypts user's cached signing key from Redis (same AES-256-GCM pattern as `signing.ts`)
  - `getUserPubkey()` — fetches user's nostr pubkey from DB
  - `addToTransmission()` / `removeFromTransmission()` — Transmission RPC integration (same 409-retry pattern as catalog upload)

#### `src/routes.ts` — Express router
- `POST /upload` — multer single file upload, parses optional `tags` JSON from body, calls `uploadFile()`
- `GET /entries` — calls `listEntries()`, returns decrypted entries + quota
- `DELETE /entries/:entryId` — calls `deleteEntry()`, returns `{ success: true }`
- `GET /entries/:entryId/torrent` — calls `getTorrentFile()`, returns buffer with `application/x-bittorrent` content type

#### `src/index.ts` — Barrel exports
- Exports `lockerRouter`, `getLockerConfig`, `LockerConfig` type

### Auth Package: NIP-44 Exports (`server/packages/auth/src/index.ts`)
- Added export of `nip44Encrypt`, `nip44Decrypt`, `getConversationKey` from `./nip44.js`
- These were implemented in Phase 9.2 but not yet exported from the package

### Server Entry: Route Mounting (`server/src/index.ts`)
- Import `lockerRouter` from `@boilerdeck/locker`
- Mount at `app.use("/api/locker", lockerRouter)`

### Server Dependencies (`server/package.json`)
- Added `"@boilerdeck/locker": "*"` to dependencies

## API Endpoints

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | `/api/locker/upload` | JWT | Upload file to locker (multipart, max 5 GB) |
| GET | `/api/locker/entries` | JWT | List user's decrypted locker entries + quota |
| DELETE | `/api/locker/entries/:entryId` | JWT | Delete entry (NIP-09 + cleanup marker) |
| GET | `/api/locker/entries/:entryId/torrent` | JWT | Download .torrent file |

## Key Design Decisions

- **Separate locker config:** Locker env vars (`LOCKER_DIR`, `LOCKER_MAX_FILE_SIZE`, `LOCKER_QUOTA_GB`) are read by `getLockerConfig()` in the locker package, not added to the global `shared/config.ts` schema. This avoids requiring these env vars in every environment.
- **Filesystem-based quota:** Quota is calculated by recursively summing file sizes in `LOCKER_DIR/<userId>/`. This is a placeholder — Phase 9.4 adds Prisma-based quota tracking for performance.
- **Deferred cleanup:** File deletion uses a `.deleted` marker file instead of immediate removal. The Phase 9.10 cleanup cron will handle actual deletion after a grace period.
- **Transmission RPC pattern:** Identical 409-retry pattern as `catalog/upload.ts` — first request gets a session ID, second request uses it.
- **Self-custody rejection:** `getUserPrivkeyHex()` throws `UnauthorizedError` for self-custody users. They must manage locker operations client-side (Phase 9.5).
- **NIP-09 for deletion:** Kind 5 deletion events are published via the user's signing key, not an admin key. This follows Nostr protocol — authors can delete their own events.
