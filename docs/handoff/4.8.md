# Sub-task 4.8 — Comment Events (Kind 1 with Tags)

## What was built
- **`server/packages/relay/src/routes.ts`** (MODIFIED) — Added two new REST endpoints:
  - `POST /api/events/:eventId/replies` (authenticated) — submit a reply to any event, creates kind 1 event with `["e", parentEventId]` tag
  - `GET /api/events/:eventId/replies` (public) — get threaded replies for an event, up to 3 levels deep

## Key decisions made during implementation

- **Kind 1 (text note) with `["e", parentEventId]` tag.** This follows the NIP-10 convention where `e` tags reference parent events. The content is plain text (not JSON), unlike reviews which JSON-stringify their content.

- **In-memory tag filtering.** The shared `queryEvents` doesn't support tag filtering, and Prisma's JSON path queries don't handle nested array matching (`[["e","<id>"]]`) well. Instead, we query kind 1 events from Prisma (limited to 500 per level) and filter in application code by checking `e` tags. This is practical because comment volume per event is bounded.

- **3-level threading built bottom-up.** Level 1 = direct replies to the target event. Level 2 = replies to level-1 events. Level 3 = replies to level-2 events. The tree is built bottom-up: level 3 nodes are leaf nodes, level 2 nodes get level 3 children attached, level 1 nodes get level 2 children attached.

- **Three separate DB queries (one per level).** Each level query is scoped to find replies to the IDs from the previous level. This avoids loading the entire kind 1 event set and allows the DB to handle ordering.

- **Parent event existence check on both endpoints.** Both POST and GET return 404 if the parent event doesn't exist, matching the spec.

## How it works

### POST /api/events/:eventId/replies (authenticated)
1. Validates `content` is a non-empty string
2. Fetches parent event by ID — 404 if not found
3. Creates kind 1 event with `content: content.trim()` and `tags: [["e", parentEventId]]`
4. Signs via `signEventForUser`, stores via `storeEvent`
5. Fans out to WS subscribers, federates outbound
6. Returns the full signed event with 201 status

### GET /api/events/:eventId/replies (public, no auth)
1. Fetches parent event by ID — 404 if not found
2. Queries level 1: kind 1 events with `["e", eventId]` tag
3. Queries level 2: kind 1 events with `["e", <level1Id>]` tags
4. Queries level 3: kind 1 events with `["e", <level2Id>]` tags
5. Builds nested tree structure bottom-up
6. Returns `{ replies: ReplyNode[] }` where each `ReplyNode` has `{ id, pubkey, content, created_at, replies: ReplyNode[] }`

### Response shape
```typescript
interface ReplyNode {
  id: string;       // event ID
  pubkey: string;   // author's pubkey
  content: string;  // reply text (plain string)
  created_at: number; // unix timestamp
  replies: ReplyNode[]; // nested replies (up to 2 more levels)
}

// GET response:
{ replies: ReplyNode[] }

// POST response: full SignedEvent object
{ id, pubkey, created_at, kind, tags, content, sig }
```

## Gotchas and surprises

- **Kind 1 events are regular (not replaceable).** Unlike reviews (kind 31337), text notes don't have replaceable semantics. Each reply creates a new event — users can post multiple replies to the same parent.

- **The `findReplies` helper queries all kind 1 events with `take: 500`.** This is a practical limit. If a system accumulates thousands of kind 1 events, this could miss some replies. For production scale, a dedicated `e_tag` column or index would be better, but for current use this is sufficient.

- **Express 5 param typing.** `req.params.eventId` is typed as `string | string[]` in Express 5, so we wrap with `String()`.

## How to use / test

### Submit a reply
```bash
curl -X POST https://boilerdeck.com/api/events/<eventId>/replies \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"content": "Great review, I agree!"}'
```

### Get replies (threaded)
```bash
curl https://boilerdeck.com/api/events/<eventId>/replies
```

### Thread a reply to a reply
```bash
# First, get the reply event ID from the POST response above
curl -X POST https://boilerdeck.com/api/events/<replyEventId>/replies \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"content": "Thanks for agreeing!"}'
```

### Verification checks
- POST with valid content -> 201, kind 1 event with `["e", parentEventId]` tag
- GET returns `{ replies: [...] }` with nested structure
- Reply to a reply -> both appear in threaded structure when fetching replies of the original parent
- Display depth limited to 3 levels (level 1 -> level 2 -> level 3, no deeper)
- POST to nonexistent eventId -> 404
- GET for nonexistent eventId -> 404
- POST without auth -> 401

## What the next sub-task needs to know

- **4.9 (Moderation)** should consider filtering muted users' replies from the threaded response. Currently all replies are returned regardless of mute status.
- The reply events are standard kind 1 text notes and will be picked up by any NIP-01 compatible client that subscribes to kind 1 events with `#e` tag filters.
- The `findReplies` helper loads up to 500 kind 1 events per level query. If comment volume grows significantly, consider adding a dedicated `e_tag` indexed column to the Event model for efficient tag-based queries.
