# Sub-task 3.6 — Server-Side Event Signing (for Web Users)

## What was built
- **`server/packages/relay/src/routes.ts`** (MODIFIED) — Added `POST /api/events/sign-and-publish` endpoint
- **`server/packages/relay/src/ws.ts`** (MODIFIED) — Exported `fanOutEvent()` (was module-private)
- **`server/packages/relay/src/index.ts`** (MODIFIED) — Added `fanOutEvent` to barrel exports

## Key decisions made during implementation
- **Reuse `signEventForUser` from auth/signing.ts.** No need to duplicate signing logic — the existing function loads the user's cached signing key from Redis, decrypts it, and creates a fully signed event.
- **Export `fanOutEvent` rather than creating event bus.** The simplest approach — direct function call. If federation (3.8/3.9) needs more complex broadcasting, an event bus can be added later.
- **Return full signed event.** The response body is the complete `SignedEvent` object, so clients can immediately use it (verify, display, etc.) without a second fetch.

## How it works

### POST /events/sign-and-publish
1. Authenticate user via JWT
2. Validate input: `kind` (non-negative integer), `content` (string, <1MB), `tags` (array, <1000)
3. Call `signEventForUser(userId, { kind, tags, content })` from `@boilerdeck/auth`
   - Loads encrypted signing key from Redis (`signing_key:{userId}`)
   - Decrypts with `SIGNING_CACHE_KEY`
   - Creates and signs a NIP-01 event with user's pubkey
4. Store event via relay `storeEvent` (handles replaceable semantics)
5. Materialize into legacy tables (non-fatal)
6. `fanOutEvent(event)` — push to all WebSocket connections with matching subscriptions
7. Return 201 with the full signed event

### Fan-out flow
```
REST POST /events/sign-and-publish
  → signEventForUser(userId, params)
  → storeEvent(event)
  → materializeEvent(event)  // non-fatal
  → fanOutEvent(event)       // pushes to all matching WS subscribers
  → 201 { id, pubkey, created_at, kind, tags, content, sig }
```

## Gotchas and surprises
- `signEventForUser` throws `UnauthorizedError` if the user is in SELF_CUSTODY mode or has no cached signing key. These surface as 401 errors to the client.
- `fanOutEvent` must be called AFTER `storeEvent` succeeds, not before.

## How to use / test
```bash
# Login first (to cache signing key)
LOGIN=$(curl -s -X POST https://boilerdeck.com/api/auth/login -H "Content-Type: application/json" -d '{"email":"test@test.com","password":"pass"}')
TOKEN=$(echo $LOGIN | jq -r .accessToken)

# Sign and publish
curl -s -X POST https://boilerdeck.com/api/events/sign-and-publish \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"kind":1,"content":"Hello from the gateway!","tags":[]}' | jq .

# Verify event stored
EVENT_ID="<id from above>"
curl -s https://boilerdeck.com/api/events/$EVENT_ID | jq .
```

## What the next sub-task needs to know
- `fanOutEvent` is now exported from `@boilerdeck/relay`. Sub-tasks 3.8/3.9 (federation) can import and call it for broadcasting federated events.
- The sign-and-publish endpoint is at `/events/sign-and-publish` (mounted under `/api` prefix).
- Self-custody users cannot use this endpoint — they must sign client-side and publish via WebSocket or `POST /events`.
