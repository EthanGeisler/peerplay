# 9.5 — Client Locker Upload (Electron)

## Summary

Created `client/src/main/lockerManager.ts` — the Electron main process module for data locker operations. Supports both custodial (server-managed) and self-custody (local key) upload paths, plus entry listing, deletion, and download via WebTorrent. Added 5 IPC handlers, preload bridge exposure, and renderer type declarations. All types pass (`npx tsc --noEmit`).

## What Changed

### New File: `client/src/main/lockerManager.ts`

Main locker module with 5 exported functions:

- **`uploadFile(tags?)`** — Opens native file dialog, uploads selected file. Custodial path uploads to `POST /api/locker/upload` (multipart form data). Self-custody path creates torrent locally via WebTorrent `seed()`, encrypts with NIP-44 (from `nip44.ts`), signs event locally (from `keyManager.ts`), publishes to relay via WebSocket, and uploads raw file to VPS for persistent seeding. Returns `LockerEntry | null` (null if user cancels).

- **`uploadDirectory(tags?)`** — Opens native directory dialog, zips contents (via `archiver` if available, else PowerShell/system `zip`), then follows same upload flow as `uploadFile`. Temp zip is cleaned up after upload.

- **`getEntries()`** — Fetches entries from `GET /api/locker/entries`. Returns `{ entries: LockerEntry[], quota: { used, max } }`.

- **`deleteEntry(entryId)`** — Deletes via `DELETE /api/locker/entries/:entryId`.

- **`downloadEntry(entryId, downloadPath)`** — Fetches `.torrent` file from `GET /api/locker/entries/:entryId/torrent`, downloads via WebTorrent to the specified path. Returns local file path.

Additional exports:
- **`setMainWindow(win)`** — Sets BrowserWindow reference for progress events
- **`setAccessToken(token)`** — Caches the access token from the renderer (since the renderer holds tokens in-memory via `@boilerdeck/ui-shared`)

#### Upload Progress
- Streams file upload with progress tracking
- Emits `locker:upload-progress` IPC events: `{ entryId, percent, bytesUploaded, bytesTotal }`
- Renderer can listen via `window.boilerdeck.locker.onUploadProgress(callback)`

#### Self-Custody Detection
Self-custody mode is detected by: `keyManager.hasKey() && !storeGet("relayPrivkey")` — the user has a local key but no server-cached relay key.

#### Self-Custody Upload Flow
1. Compute SHA-256 of file locally
2. Detect MIME type from extension
3. Create torrent via WebTorrent `seed()` (uses bundled `create-torrent`)
4. Build `LockerEntry` JSON
5. Encrypt with NIP-44 to own pubkey (`nip44.ts`)
6. Sign Nostr event locally (`keyManager.signEvent()`)
7. Publish to relay via WebSocket (`relayManager.publish()`)
8. Upload raw file + `.torrent` to VPS for persistent seeding (non-fatal — failure doesn't block the upload)

### IPC Handlers (in `client/src/main/index.ts`)

All handlers receive the access token as the first argument (after `_event`), since tokens are managed in-memory by the renderer's API client:

| Channel | Parameters | Returns |
|---------|-----------|---------|
| `locker:upload-file` | `accessToken, tags?` | `LockerEntry \| null` |
| `locker:upload-directory` | `accessToken, tags?` | `LockerEntry \| null` |
| `locker:get-entries` | `accessToken` | `{ entries, quota }` |
| `locker:delete-entry` | `accessToken, entryId` | `void` |
| `locker:download-entry` | `accessToken, entryId, downloadPath` | `string` (local path) |

Push event (main → renderer):
| Channel | Data |
|---------|------|
| `locker:upload-progress` | `{ entryId, percent, bytesUploaded, bytesTotal }` |

## Key Design Decisions

- **Access token passed via IPC:** The renderer's API client (`@boilerdeck/ui-shared`) manages tokens in-memory. The main process caches the token via `setAccessToken()` before each operation. This avoids storing tokens in the persistent JSON store (security) and avoids duplicating the token refresh logic.

- **Multipart upload streaming:** File uploads use raw `http.request` with manual multipart boundary construction and `fs.createReadStream`, enabling progress tracking without buffering the entire file. Timeout is 5 minutes for large files.

- **WebTorrent for torrent creation:** Instead of adding `create-torrent` as a separate dependency, the self-custody path uses WebTorrent's `seed()` method (which internally uses `create-torrent`). A temporary WebTorrent client is created, seed is called, torrent metadata is extracted, then the client is destroyed.

- **Self-custody VPS upload is non-fatal:** The raw file upload to VPS for persistent seeding uses `resolve()` instead of `reject()` on failure. The file is already published to the relay and the user is seeding locally — VPS seeding is a convenience, not a requirement.

- **MIME detection via extension map:** Uses a built-in map of common extensions instead of adding a dependency like `mime-types`. Defaults to `application/octet-stream` for unknown types.

- **Directory upload zips first:** Uses `archiver` (dynamic import, fallback to PowerShell `Compress-Archive` on Windows or `zip` CLI on Linux/Mac). Temp zip is always cleaned up in a `finally` block.

- **API error parsing follows project convention:** Server returns `{ error: { code, message } }`. Error parsing tries `body.error.message`, then `body.message`, then falls back to HTTP status text — matching the convention documented in CLAUDE.md.
