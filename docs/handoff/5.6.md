# Sub-task 5.6 — Web of Trust Weighting

## What was built
- **`server/packages/relay/src/reputation.ts`** (MODIFIED) — Extended `getReputation()` to accept an optional `viewerPubkey` parameter for personalized web-of-trust scoring. Added helper functions `getFollowedPubkeys()`, `getMutedPubkeys()`, and `getTrustWeight()`.
- **`server/packages/relay/src/routes.ts`** (MODIFIED) — Updated `GET /reputation/:pubkey` route to accept optional `viewer` query parameter and pass it to `getReputation()`.

## Key decisions made during implementation

- **Follow list from kind 3 events.** The viewer's follow list is fetched by querying the latest kind 3 event for the viewer's pubkey via `queryEvents()`, then extracting `["p", pubkey]` tags. This reuses the existing event store infrastructure from 4.6.

- **Mute list from Redis sets.** Mute lists are stored as `mute_list:{userId}` in Redis (from 4.9). Since the viewer is identified by pubkey but mute lists are keyed by userId, we do a `db.user.findFirst({ where: { nostrPubkey: viewerPubkey } })` to map pubkey to userId first.

- **Trust weight applied before the log formula.** The trust multiplier is applied to the MB weight (after anti-sybil adjustments) but before `Math.log2(1 + weight)`. This means unknown users (0.25x) contribute significantly less to the score, while muted users (0x) are completely skipped.

- **Separate cache keys for personalized scores.** Global scores use `reputation:{pubkey}`, personalized scores use `reputation:{pubkey}:viewer:{viewerPubkey}`. Both use the same 15-minute TTL.

- **Parallel fetching of follow/mute lists.** When a viewer is specified, both the follow list and mute list are fetched concurrently with `Promise.all()`.

## How it works

### Trust weight multipliers
| Relationship | Weight |
|---|---|
| Followed (viewer follows the attester) | 1.0x |
| Unknown (not followed, not muted) | 0.25x |
| Muted (viewer has muted the attester) | 0x (skipped entirely) |

### Flow (personalized)
1. Check Redis cache at `reputation:{pubkey}:viewer:{viewerPubkey}`
2. If miss: query all kind 31338 attestation events for target pubkey
3. Fetch viewer's follow list (kind 3 event `p` tags) and mute list (Redis set) in parallel
4. For each attestation:
   - Apply daily rate limit (max 20 per attester per day)
   - Parse `bytesDownloaded` from content
   - Apply new account penalty (< 7 days → 0.1x)
   - Apply trust weight based on attester's relationship to viewer
   - If muted: skip entirely; if unknown: 0.25x; if followed: 1.0x
   - Accumulate `log2(1 + weight)`
5. Cache and return

### Flow (global — unchanged)
When no `viewer` param is provided, behavior is identical to pre-5.6. No trust weighting is applied.

### Route
```
GET /api/reputation/:pubkey                    → global (unweighted) score
GET /api/reputation/:pubkey?viewer=<pubkey>    → personalized (trust-weighted) score
```

Both return: `{ pubkey, score, attestationCount, uniqueAttesters }`

### Key function signatures
```typescript
// reputation.ts
export async function getReputation(
  pubkey: string,
  viewerPubkey?: string,
): Promise<ReputationScore>
```

## Gotchas and surprises

- **Mute list keyed by userId, not pubkey.** The mute list Redis sets use `mute_list:{userId}`, so we need a DB lookup to map `viewerPubkey` to `userId` before checking mutes. If the viewer pubkey doesn't correspond to any user, an empty mute set is returned (no muting applied).

- **`attestationCount` and `uniqueAttesters` reflect the personalized view.** When a viewer is specified, muted attesters are excluded from the count. This accurately reflects what the viewer "sees" in terms of reputation.

## How to use / test

### Global score (no viewer)
```bash
curl https://boilerdeck.com/api/reputation/<64-char-hex-pubkey>
```

### Personalized score (with viewer)
```bash
curl "https://boilerdeck.com/api/reputation/<target-pubkey>?viewer=<viewer-pubkey>"
```

### Verify different scores
If the viewer follows some attesters but not others, the personalized score should differ from the global score (unknown attesters weighted 0.25x instead of 1.0x).

### Invalid viewer param
```bash
curl "https://boilerdeck.com/api/reputation/<pubkey>?viewer=invalid"
# → 400: "viewer must be a 64-character hex pubkey"
```

## What the next sub-task needs to know
- **`getReputation(pubkey, viewerPubkey?)` signature is backwards-compatible.** Calling without a viewer returns the same global score as before.
- **Cache keys are separate** for global and personalized scores. Clearing the global cache won't affect personalized caches and vice versa.
- **The personalized score uses the same `ReputationScore` type** — no new types were added.
- **Phase 6+ can use this** to show personalized reputation in UI by passing the logged-in user's pubkey as the viewer.
