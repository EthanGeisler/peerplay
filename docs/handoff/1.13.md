# Sub-task 1.13 — Password change flow

## What was built
- **`server/packages/auth/src/schemas.ts`** — added `changePasswordSchema` and `ChangePasswordInput` type
- **`server/packages/auth/src/service.ts`** — added `changePassword()` function
- **`server/packages/auth/src/routes.ts`** — added `POST /api/auth/change-password` (authenticated)

## Key decisions made during implementation
- **Decrypt-then-re-encrypt, not update-in-place.** The encrypted keys use random salt+nonce, so there's no way to "swap" the password without fully decrypting and re-encrypting. This means two scrypt calls (decrypt old + encrypt new) per key — ~200-400ms total blocking time.
- **Conditional re-encryption via null guards.** `if (user.encryptedNsec)` and `if (user.encryptedMnemonic)` naturally handle self-custody users (who have no encrypted keys) without a separate code path. Self-custody users only get their bcrypt hash updated.
- **All refresh tokens invalidated.** `deleteMany({ where: { userId } })` wipes every session, forcing re-login on all devices. This is the safest approach — a password change should invalidate all existing sessions.
- **Redis signing key cleared.** The cached signing key was encrypted with the server's `SIGNING_CACHE_KEY` (not the user's password), so it's still technically valid, but clearing it forces re-caching on next login with the new password. This keeps the flow clean and predictable.

## How it works

### Password change flow
```
POST /api/auth/change-password  [Authorization: Bearer <token>]
  { currentPassword, newPassword }
  → verify currentPassword (bcrypt)
  → hash newPassword (bcrypt)
  → if encryptedNsec: decrypt with currentPassword → re-encrypt with newPassword
  → if encryptedMnemonic: decrypt with currentPassword → re-encrypt with newPassword
  → db.user.update: passwordHash, encryptedNsec?, encryptedMnemonic?
  → db.refreshToken.deleteMany({ userId })  // invalidate all sessions
  → redis.del("signing_key:{userId}")       // clear cached signing key
  → return { message: "Password changed successfully" }
```

### Schema
```ts
changePasswordSchema = z.object({
  currentPassword: z.string().min(1),   // can't be empty
  newPassword: z.string().min(8),       // same min as registration
})
```

## Gotchas and surprises
- **Two scrypt calls per key.** `decryptPrivateKey` runs scrypt to derive the decryption key from the old password, then `encryptPrivateKey` runs scrypt again to derive the encryption key from the new password. Same for mnemonic. That's up to 4 scrypt calls for a custodial user. Each takes ~50-100ms with N=32768.
- **The update is not wrapped in a DB transaction.** If the server crashes between `db.user.update` and `db.refreshToken.deleteMany`, the password is changed but old sessions are still valid. This is an acceptable failure mode — the sessions will eventually expire naturally.

## How to test
```bash
# Change password (custodial user)
TOKEN=$(curl -s -X POST https://boilerdeck.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"oldpass123"}' | jq -r .accessToken)

curl -s -X POST https://boilerdeck.com/api/auth/change-password \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"currentPassword":"oldpass123","newPassword":"newpass123"}'

# Verify login with new password works
curl -s -X POST https://boilerdeck.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"newpass123"}'
```
