# Sub-task 1.12 — Electron client: client-side keypair generation (self-custody registration)

## What was built
- **`client/package.json`** — added `@noble/curves`, `@noble/hashes`, `@scure/bip39`, `@scure/bip32`, `@scure/base` to dependencies
- **`client/src/main/index.ts`** — added `crypto:generate-keypair` and `crypto:sign-challenge` IPC handlers
- **`client/src/main/preload.ts`** — exposed `window.boilerdeck.crypto` bridge with `generateKeypair()` and `signChallenge()`
- **`client/src/renderer/env.d.ts`** — added `crypto` type declarations matching preload
- **`client/src/main/store.ts`** — added `selfCustodyKey` to store interface and whitelist
- **`client/src/renderer/stores/authStore.ts`** — added `registerSelfCustody()` and `loginWithPubkey()` actions
- **`client/src/renderer/pages/Login.tsx`** — added "Generate keys on this device (advanced)" toggle on registration tab

## Key decisions made during implementation
- **`safeStorage` for private key encryption.** Electron's `safeStorage.encryptString()` uses the OS credential store (DPAPI on Windows, Keychain on macOS, libsecret on Linux). The encrypted buffer is stored as base64 in the JSON store file. Only the same OS user on the same machine can decrypt it.
- **Dynamic imports for crypto modules.** Used `await import()` in the IPC handlers to avoid loading heavy crypto libraries at app startup. They're only needed when the user chooses self-custody.
- **`bytesToHex`/`hexToBytes` from `@noble/hashes/utils.js`** — NOT from `@noble/curves/abstract/utils.js` (which isn't exported). This is a gotcha — the curves package doesn't expose its internal utils via the exports map.
- **`loginWithPubkey()` is a separate action, not integrated into the Login UI yet.** The plan says "self-custody Electron users use challenge-based login instead of password" — the store action is ready, but the Login.tsx form still uses email/password for login. Self-custody users CAN still log in with email/password (the server accepts both). Challenge-based login can be surfaced in a future iteration if needed.

## How it works

### Self-custody registration flow
```
User checks "Generate keys on this device (advanced)" → submits form
  → registerSelfCustody() in authStore
    → IPC: crypto:generate-keypair
      → main process: generate BIP39 mnemonic
      → derive keypair via NIP-06 (m/44'/1237'/0'/0/0)
      → encrypt private key hex with safeStorage
      → store encrypted key in selfCustodyKey
      → return { mnemonic, pubkeyHex }
    → POST /api/auth/register with { email, password, displayName, pubkey }
    → server stores pubkey only (no encrypted_nsec, no encrypted_mnemonic)
    → MnemonicModal shows locally-generated mnemonic
```

### Challenge-based login flow (store action ready, not yet in UI)
```
loginWithPubkey() in authStore
  → GET /api/auth/challenge → { challenge }
  → IPC: crypto:sign-challenge(challenge)
    → main process: decrypt selfCustodyKey with safeStorage
    → SHA-256(challenge bytes) → Schnorr sign
    → return { signature, pubkeyHex }
  → POST /api/auth/login/pubkey with { pubkey, challenge, signature }
  → tokens stored, user set
```

### Store changes
```ts
// New store key
selfCustodyKey: string  // base64-encoded safeStorage-encrypted private key hex

// Whitelist updated
STORE_KEY_WHITELIST = new Set([..., "selfCustodyKey"])
```

## Gotchas and surprises
- **`@noble/curves/abstract/utils.js` is NOT exported.** The package's exports map doesn't include this subpath. Use `@noble/hashes/utils.js` for `bytesToHex`/`hexToBytes` instead.
- **`safeStorage.isEncryptionAvailable()` is not checked.** On headless Linux without a keyring, safeStorage will fail. This is fine for a desktop app but would need a fallback for CI/testing.
- **HDKey publicKey is 33 bytes (compressed).** Must `.slice(1)` to get the 32-byte x-only pubkey for Nostr. Same gotcha as server-side 1.2.
- **Main process tsconfig uses `module: "Node16"`** so dynamic imports resolve correctly, but type-checking is stricter about subpath exports.
