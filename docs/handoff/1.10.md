# Sub-task 1.10 — Frontend: mnemonic display on first login migration (web)

## What was built
- **`web/src/stores/authStore.ts`** — `login()` return type changed from `Promise<void>` to `Promise<string | undefined>`, now returns `data.mnemonic` from the API response
- **`web/src/pages/Login.tsx`** — login handler now captures the mnemonic and shows `MnemonicModal` instead of navigating immediately (same pattern as registration)

## Key decisions made during implementation
- **Reused the exact same pattern as registration.** The register path already did `const m = await register(...)` → `if (m) setMnemonic(m) else navigate("/")`. Login now does the same thing with `login()`. No new components or state needed.
- **No new components.** `MnemonicModal` was already imported in Login.tsx and wired to the `mnemonic` state. The only gate was that `login()` wasn't returning the mnemonic.

## How it works

### Login flow (pre-migration user, first login after Phase 1)
```
User logs in → login() API call
  → API returns { user, accessToken, refreshToken, mnemonic }  (mnemonic present because 1.6 lazy migration ran)
  → Tokens stored, user set in store
  → mnemonic returned from login()
  → Login.tsx captures it in local state → MnemonicModal renders
  → User saves phrase → checks checkbox → clicks "Continue"
  → mnemonic cleared from state → navigate("/")
```

### Login flow (user with existing keypair)
```
User logs in → login() API call
  → API returns { user, accessToken, refreshToken }  (no mnemonic)
  → login() returns undefined
  → navigate("/") immediately
```

## Gotchas and surprises
- None — this was a clean two-file change. The infrastructure from 1.9 (MnemonicModal, mnemonic state, conditional rendering) made this trivial.

## How to use / test
- Login with a pre-migration user (one created before Phase 1.4, without a keypair) → mnemonic modal should appear
- Login again with the same user → no mnemonic modal (keypair already assigned on first login)
- Login with a post-Phase-1.4 user → no mnemonic modal
