# Sub-task 3.4 — WebSocket Relay Endpoint

## What was built

- **`server/packages/relay/src/index.ts`** (MODIFIED) — exports `attachRelayWebSocket`
- **`server/src/index.ts`** (MODIFIED) — captures `http.Server` from `app.listen()`, passes to `attachRelayWebSocket`
- **`server/packages/relay/package.json`** (MODIFIED) — added `ws` + `@types/ws` dependencies

## Key decisions made during implementation
- **No authentication required for WebSocket publish.** NIP-01 relays accept any event with a valid signature — the signature IS the authentication. The REST `POST /events` endpoint requires JWT auth + pubkey match, but the WebSocket endpoint follows standard Nostr relay behavior where signature verification is sufficient.
- **In-memory subscription management.** Subscriptions are stored per-connection in a `Map<string, EventFilter[]>`. No Redis or DB needed — subscriptions are ephemeral and tied to connection lifetime.
- **DB query + in-memory tag filtering.** The shared `queryEvents` only supports `kinds`, `authors`, `since`, `until`, `limit`. NIP-01 also requires `ids`, `#e`, `#p` filtering. We query the DB with what it supports, then apply `ids`/`#e`/`#p` filters in-memory via `matchesFilter()`. This is sufficient for current scale.
- **NIP-01 prefix matching for `ids` and `authors`.** Per NIP-01 spec, filter `ids` and `authors` use prefix matching (e.g., `"ab"` matches `"ab12cd..."`). Implemented via `startsWith()`.
- **`maxPayload: 1MB` on WSS.** The `ws` library enforces this at the frame level — oversized messages close the connection automatically (code 1009). This handles the verification check for oversized messages.
- **Fan-out on every published event.** After storing an event, `fanOutEvent()` iterates all connections and all their subscriptions, checking each filter. One match per subscription suffices (break after first matching filter).

## How it works

### Server entry wiring
```typescript
// server/src/index.ts
const server = app.listen(config.PORT, () => { ... });
attachRelayWebSocket(server);
```
The `ws.WebSocketServer` shares the HTTP server and listens on the `/relay` path. Express continues handling REST on all other paths.

### Connection lifecycle
1. Client connects to `ws://host/relay`
2. Server creates a `ConnectionState` with unique ID and empty subscriptions map
3. Messages are dispatched by type: `REQ` → `handleReq`, `EVENT` → `handleEvent`, `CLOSE` → `handleClose`
4. On disconnect, connection is removed from the global `connections` map

### REQ flow
1. Parse subscription ID and filters from `["REQ", subId, ...filters]`
2. Check subscription limit (max 20 per connection)
3. Register/replace subscription in connection state
4. For each filter: query DB for stored events, apply in-memory tag filters, send matching events
5. Send `["EOSE", subId]` to signal end of stored events
6. From this point, live events matching the filters are pushed via fan-out

### EVENT flow
1. Parse and validate event shape from `["EVENT", signedEvent]`
2. Enforce size limits (1MB content, 1000 tags)
3. Verify Schnorr signature
4. Store event (shared eventStore handles replaceable semantics)
5. Materialize into legacy tables (non-fatal)
6. Send `["OK", eventId, true, ""]` to publisher
7. `fanOutEvent()` pushes to all matching subscribers across all connections

### CLOSE flow
1. Remove subscription from connection state by ID
2. No response sent (NIP-01 spec)

### Filter matching (`matchesFilter`)
```
ids      → event.id.startsWith(any) — NIP-01 prefix match
authors  → event.pubkey.startsWith(any) — NIP-01 prefix match
kinds    → event.kind in list
since    → event.created_at >= since
until    → event.created_at <= until
#e       → any "e" tag value in list
#p       → any "p" tag value in list
```
All specified fields must match (AND). Within a field, any value matches (OR).

## Gotchas and surprises
- **`ws` maxPayload behavior.** When a message exceeds `maxPayload`, the `ws` library closes the connection with code 1009 (message too big) rather than sending a NOTICE. This is standard WebSocket behavior and acceptable per the verification checks.
- **`satisfies` for send helpers.** Used `satisfies RelayEventMessage` etc. in send helpers for type safety without runtime overhead.
- **No `ws.close()` on error in message handler.** We send NOTICE/OK for protocol errors but keep the connection open. Only truly malformed connections (binary frames, etc.) would be closed by ws internals.

## How to use / test

### Connect with wscat
```bash
npx wscat -c ws://localhost:3000/relay
```

### Subscribe to all kind 1 events
```json
["REQ", "sub1", {"kinds": [1]}]
```
Expected: `["EOSE", "sub1"]` (no stored kind 1 events yet)

### Publish an event (requires valid signature)
```json
["EVENT", {"id":"...","pubkey":"...","created_at":1234,"kind":1,"tags":[],"content":"hello","sig":"..."}]
```
Expected: `["OK", "<id>", true, ""]`

### Publish with bad signature
```json
["EVENT", {"id":"bad","pubkey":"bad","created_at":1234,"kind":1,"tags":[],"content":"hello","sig":"bad"}]
```
Expected: `["OK", "bad", false, "invalid: signature verification failed"]`

### Nginx WebSocket proxy config
Add to the nginx server block:
```nginx
location /relay {
    proxy_pass http://127.0.0.1:3000/relay;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 86400s;
    proxy_send_timeout 86400s;
}
```
