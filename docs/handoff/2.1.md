# Sub-task 2.1 — Create events table migration

## What was built
- **`server/prisma/schema.prisma`** — added `Event` model and `eventId` foreign key on `Game`
- **`server/prisma/migrations/20260318040000_add_events_table/migration.sql`** — migration SQL

## Key decisions made during implementation
- **`migrate diff` + `migrate deploy` again.** Same approach as 1.3 — `migrate dev` doesn't work in non-interactive shells. Generated SQL with `migrate diff`, wrote to migration directory, applied with `migrate deploy`.
- **Event ID is the SHA-256 hash, not a UUID.** The `id` field has no `@default(uuid())` — it's computed by the application layer (SHA-256 of canonical NIP-01 JSON). This is the Nostr standard: event IDs are content-addressable.
- **`createdAt` is an Int, not DateTime.** NIP-01 uses Unix timestamps (seconds). Mapped to `created_at_unix` to avoid confusion with Prisma's `DateTime` fields.
- **`tags` is Json (JSONB in Postgres).** NIP-01 tags are arrays of string arrays, e.g., `[["d", "game-slug"], ["t", "game"]]`. JSONB gives us indexed queries on tag values if needed.
- **Foreign key from Game → Event uses `SET NULL` on delete.** If an event is somehow deleted, the game record survives (it's the legacy source of truth during the transition period).

## How it works

### Event model
```prisma
model Event {
  id         String   @id                          // SHA-256 hash of canonical JSON
  pubkey     String                                // 64-char hex, x-only secp256k1
  createdAt  Int      @map("created_at_unix")      // Unix timestamp (seconds)
  kind       Int                                   // 30001=listing, 30002=version, etc.
  tags       Json                                  // Array of string arrays
  content    String                                // Often JSON-stringified payload
  sig        String                                // 128-char hex Schnorr signature
  dTag       String?  @map("d_tag")                // Replaceable event identifier
  receivedAt DateTime @default(now()) @map("received_at")

  games      Game[]

  @@unique([pubkey, kind, dTag])                   // Replaceable event constraint
  @@index([kind])
  @@index([pubkey])
  @@index([createdAt])
  @@map("events")
}
```

### Game model change
```prisma
eventId     String?    @unique @map("event_id")
event       Event?     @relation(fields: [eventId], references: [id])
```

## Gotchas and surprises
- **`@@unique([pubkey, kind, dTag])` allows multiple NULLs for `dTag`.** PostgreSQL treats NULL as distinct for uniqueness, so regular events (non-replaceable, no `dTag`) won't conflict. Only parameterized replaceable events (kind 30000-39999) set `dTag`.
- **`tags` is JSONB, not JSON.** Prisma uses JSONB by default for PostgreSQL `Json` fields, which supports indexing and containment queries (`@>` operator). This will be useful for querying events by tag values in Phase 2.3.

node --import tsx --input-type=module -e "

## What the next sub-task needs to know
- The `Event` model is ready for use. Sub-task 2.2 builds `events.ts` (serializeEvent, hashEvent, createEvent, verifyEvent) in the shared package.
- `db.event.create()` requires all non-optional fields: `id`, `pubkey`, `createdAt`, `kind`, `tags`, `content`, `sig`. The `id` must be computed by the caller (SHA-256 of canonical JSON).
- The `@@unique([pubkey, kind, dTag])` constraint means upserting replaceable events needs to use `upsert` or handle P2002 errors.
- `Game.eventId` is nullable — existing games have `null`. Sub-task 2.5 will populate this when wrapping game creation in event signing.
- On VPS deployment: run `npx prisma migrate deploy` before restarting the server, then `npx prisma generate` if node_modules were reinstalled.
