# 9.9 — Locker Sharing (Encrypted to Recipient)

## Summary

Users can share individual locker entries with other BoilerDeck users. The sender's entry is decrypted, then re-encrypted with NIP-44 to the recipient's pubkey and published as a new Nostr event. Recipients discover shared entries via `#p` tag filtering. Senders can revoke shares via NIP-09 deletion.

## What Changed

### Server: `server/packages/locker/src/service.ts`

Three new exported functions:

**`shareEntry(userId, entryId, recipientPubkey)`**
1. Rate-limits: max 100 shares/hour per user (in-memory counter, resets hourly)
2. Validates sender is not sharing with themselves
3. Looks up original locker event (kind 30078, d-tag = entryId, authored by sender)
4. Decrypts the LockerEntry using sender's cached signing key
5. Re-encrypts with NIP-44 to recipient's pubkey
6. Creates a new kind 30078 event with tags:
   - `["d", newShareId]` (unique UUID for the share)
   - `["p", recipientPubkey]` (for recipient filtering)
   - `["shared-from", senderPubkey]`
   - `["shared-entry", originalEntryId]`
7. Signs with sender's key, stores in event DB
8. Returns `{ shareId, eventId }`

**`getSharedWithMe(userId)`**
1. Queries all kind 30078 events (limit 500)
2. Filters in-memory for events with `#p` tag matching user's pubkey (eventStore.queryEvents doesn't support tag-based filtering)
3. Decrypts each with user's private key using the event's pubkey (sender) as the ECDH counterparty
4. Returns `{ entries: LockerEntry[], sharedFrom: { [entryId]: senderPubkey } }`

**`revokeShare(userId, shareId)`**
1. Finds the share event (kind 30078 with d-tag = shareId AND has `shared-from` tag — this distinguishes shares from regular locker entries)
2. Publishes NIP-09 kind 5 deletion event referencing the share
3. Returns `{ success: true }`

**Rate limiting:** Simple in-memory Map with hourly reset window. No Redis needed — this is per-process and resets on restart, which is acceptable for abuse prevention.

### Server: `server/packages/locker/src/routes.ts`

Three new authenticated routes:

- `POST /share` — body: `{ entryId, recipientPubkey }`. Validates recipientPubkey is a 64-char hex string. Returns 201 with `{ shareId, eventId }`.
- `GET /shared-with-me` — returns `{ entries, sharedFrom }`.
- `DELETE /share/:shareId` — returns `{ success: true }`.

## Key Design Decisions

- **In-memory `#p` filtering:** The eventStore's `queryEvents` only supports `kinds`, `authors`, `since`, `until`, and `limit` filters. Tag-based filtering (`#p`) is done in-memory after querying all kind 30078 events. This is acceptable at current scale (max 500 events per query). A future optimization would add tag-based filtering to the Prisma query.

- **Separate event per share:** Each share creates a new kind 30078 event with its own `d`-tag (the shareId). The original entry remains untouched. This means shares and originals are independent — revoking a share doesn't affect the sender's copy.

- **Rate limiting is in-memory, not Redis:** Simple Map with hourly window. Resets on server restart. Sufficient for preventing abuse without adding Redis complexity.

- **Share identification:** Share events are distinguished from regular locker entries by the presence of a `shared-from` tag. The `revokeShare` function uses this to avoid accidentally deleting regular entries.

- **NIP-44 encryption direction:** The sender encrypts to the recipient's pubkey. The recipient decrypts using their private key + sender's pubkey (from the event's `pubkey` field) to derive the conversation key.
