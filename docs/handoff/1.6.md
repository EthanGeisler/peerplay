# Sub-task 1.6 — Lazy keypair migration for existing users

## What was built
- **`server/packages/auth/src/service.ts`** — `login()` now generates a keypair for users without one (lazy migration), returns mnemonic one-time; added `recoverMnemonic()` function
- **`server/packages/auth/src/schemas.ts`** — added `recoverMnemonicSchema`
- **`server/packages/auth/src/routes.ts`** — added `POST /api/auth/recover-mnemonic` (authenticated + password)

## Key decisions made during implementation
- **Migration happens inside `login()`, not a separate endpoint.** This keeps the UX seamless — users don't need to take any action. The mnemonic appears in the login response exactly once.
- **Signing key cache updated after migration.** After generating the keypair, the newly encrypted nsec is immediately decrypted and cached in Redis, so the user's signing key is ready for Phase 2 event signing right away.
- **`recoverMnemonic` requires password verification.** Even though the user is authenticated (JWT), we require the password again to decrypt the mnemonic. Defense in depth — a stolen JWT alone can't extract the recovery phrase.
- **No key regeneration.** There is no endpoint or logic that generates a new keypair for a user who already has one. Pubkeys are immutable.

## How it works

### Lazy migration flow
```
POST /api/auth/login { email, password }
  → verify password
  → if user.nostrPubkey is null:
      → generateKeypair() → { mnemonic, publicKey, privateKey }
      → encrypt privkey + mnemonic with password
      → db.user.update() with nostrPubkey, encryptedNsec, encryptedMnemonic, CUSTODIAL
      → set mnemonic for one-time return
  → cache signing key in Redis (if custodial)
  → return { user: { ...existing, nostrPubkey }, accessToken, refreshToken, mnemonic? }
```

Second login: user now has `nostrPubkey`, so migration block is skipped, no mnemonic in response.

### Recover mnemonic
```
POST /api/auth/recover-mnemonic  [Authorization: Bearer <token>]
  { password }
  → verify password (bcrypt)
  → if self-custody → 400
  → if no encryptedMnemonic → 400
  → decryptMnemonic(encryptedMnemonic, password)
  → return { mnemonic }
```

## Gotchas and surprises
- **Cache condition updated.** The signing key cache check now uses `|| !user.nostrPubkey` to handle the case where a freshly migrated user doesn't have `custodyMode` set on the in-memory `user` object (it was just updated in DB but the local variable still has the old value).
- **`generateAccessToken` uses spread with updated pubkey.** After migration, we pass `{ ...user, nostrPubkey }` so the JWT gets the new pubkey even though the original `user` object from the DB query had `nostrPubkey: null`.

## How to test
```bash
# Create user without keypair directly in DB, then login
# (or use any pre-existing user from before Phase 1.4)

# Login — should get mnemonic in response
curl -s -X POST https://boilerdeck.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"<pre-migration-user>","password":"<password>"}'

# Login again — should NOT get mnemonic
curl -s -X POST https://boilerdeck.com/api/auth/login ...

# Recover mnemonic
curl -s -X POST https://boilerdeck.com/api/auth/recover-mnemonic \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"password":"<password>"}'
```
