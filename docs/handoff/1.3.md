# Sub-task 1.3 — Database migration: add keypair columns to User

## What was built
- **`server/prisma/schema.prisma`** — added `CustodyMode` enum and 4 new columns to User model
- **`server/prisma/migrations/20260317184846_add_keypair_identity/migration.sql`** — Prisma migration file

## Key decisions made during implementation
- **`migrate diff` + `migrate deploy` instead of `migrate dev`:** Prisma's `migrate dev` requires an interactive TTY. Used `prisma migrate diff --from-schema-datasource --to-schema-datamodel --script` to generate the exact SQL, wrote it to a migration directory, then applied with `prisma migrate deploy`. Result is identical to what `migrate dev` would produce.
- **Enum placement:** `CustodyMode` enum placed after `PaymentStatus` (alongside other enums at the top of the schema), before models.
- **Column ordering:** New columns placed after `stripeCustomerId`, before `createdAt` — logically grouped with user identity fields.

## How it works

### New enum
```prisma
enum CustodyMode {
  CUSTODIAL      // Server holds encrypted private key
  SELF_CUSTODY   // User holds their own key, server only has pubkey
  @@map("custody_mode")
}
```

### New User columns
```prisma
nostrPubkey       String?      @unique @map("nostr_pubkey")    // 64-char hex, x-only secp256k1
encryptedNsec     String?      @map("encrypted_nsec")          // AES-256-GCM encrypted private key (v1: format)
encryptedMnemonic String?      @map("encrypted_mnemonic")      // AES-256-GCM encrypted 12-word mnemonic
custodyMode       CustodyMode  @default(CUSTODIAL) @map("custody_mode")
```

### Migration SQL
```sql
CREATE TYPE "custody_mode" AS ENUM ('CUSTODIAL', 'SELF_CUSTODY');
ALTER TABLE "users"
  ADD COLUMN "custody_mode" "custody_mode" NOT NULL DEFAULT 'CUSTODIAL',
  ADD COLUMN "encrypted_mnemonic" TEXT,
  ADD COLUMN "encrypted_nsec" TEXT,
  ADD COLUMN "nostr_pubkey" TEXT;
CREATE UNIQUE INDEX "users_nostr_pubkey_key" ON "users"("nostr_pubkey");
```

## Gotchas and surprises
- **`prisma migrate dev` fails in non-interactive shells** — even with `--create-only` and piped input. The workaround is `migrate diff` to generate SQL + `migrate deploy` to apply. This will likely be needed for all future migrations in this environment.
- **`prisma db execute` produces no visible output** — it runs the SQL but doesn't print result rows. Use the Prisma client (or psql) to verify query results.
- **`nostrPubkey` unique constraint on nullable column** is fine in PostgreSQL — `NULL` values are not considered equal for uniqueness, so multiple users can have `NULL` pubkeys during the migration period.


## What the next sub-task needs to know
- The Prisma client now has `nostrPubkey`, `encryptedNsec`, `encryptedMnemonic`, and `custodyMode` on the User model. Use them in `db.user.create()` and `db.user.update()`.
- `custodyMode` is a Prisma enum — use `CustodyMode.CUSTODIAL` or `CustodyMode.SELF_CUSTODY` (import from `@prisma/client`). Or use the string literals `"CUSTODIAL"` / `"SELF_CUSTODY"` — Prisma accepts both.
- `nostrPubkey` has a unique constraint — attempting to insert a duplicate will throw a Prisma `P2002` error.
- All three nullable columns (`nostrPubkey`, `encryptedNsec`, `encryptedMnemonic`) are `null` for existing users. Sub-task 1.4 populates them on registration; 1.6 populates them lazily on login for existing users.
- On VPS deployment: run `npx prisma migrate deploy` before restarting the server. Then `npx prisma generate` if node_modules were reinstalled.
