# 9.4 — Prisma Schema & Storage Tracking

## Summary

Added `LockerFile` and `LockerQuota` Prisma models for DB-based storage tracking. The locker service now creates a `LockerFile` record on upload, performs quota checks against the database (not filesystem), soft-deletes records on entry deletion, and returns quota info from DB in the list response. This replaces the filesystem-based `getUserStorageBytes()` calls from Phase 9.3 with proper database-backed tracking.

## What Changed

### Prisma Schema (`server/prisma/schema.prisma`)
- Added `LockerFile` model — tracks each uploaded file (userId, entryId, filename, size as BigInt, infoHash, torrentPath, filePath, soft-delete via `deletedAt`)
- Added `LockerQuota` model — per-user quota tracking (usedBytes, maxBytes as BigInt, one row per user)
- Added `lockerFiles LockerFile[]` and `lockerQuota LockerQuota?` relations to `User` model
- All fields use `@@map` / `@map` for snake_case DB names (matches Phase 7 convention)

### Migration (`server/prisma/migrations/20260319051028_add_locker_tables/`)
- Creates `locker_files` table with unique index on `entry_id` and regular index on `user_id`
- Creates `locker_quotas` table with unique index on `user_id`
- Foreign keys to `users` table on both

### Storage (`server/packages/locker/src/storage.ts`)
- Added `getQuota(userId)` — upserts a `LockerQuota` record (creates with 50 GB default max if none exists), returns `{ used: bigint, max: bigint }`
- Added `incrementQuota(userId, fileSize)` — upserts quota, incrementing `usedBytes`
- Added `decrementQuota(userId, fileSize)` — decrements `usedBytes` (floors at 0)
- `getUserStorageBytes()` and `getDirectorySize()` remain as filesystem fallback but are no longer called by the service

### Service (`server/packages/locker/src/service.ts`)
- **Upload:** Quota check now reads from DB via `storage.getQuota()`. After successful upload, creates `LockerFile` record and calls `storage.incrementQuota()`. Stores `torrentPath` and `filePath` in the record.
- **List:** Quota returned from `storage.getQuota()` instead of filesystem scan. Values converted from BigInt to Number for JSON serialization.
- **Delete:** Soft-deletes the `LockerFile` record (sets `deletedAt`) and decrements quota via `storage.decrementQuota()`. Physical file cleanup still deferred to Phase 9.10 cron.
- Removed `getLockerConfig` import (no longer needed for quota calculation in service)

## Key Design Decisions

- **BigInt throughout:** File sizes and quota values use Prisma `BigInt` (PostgreSQL `bigint`) to support files > 2 GB without precision loss. Converted to `Number` only at the API response boundary.
- **Upsert for quota:** `getQuota()` uses `upsert` to lazily create quota records — no migration backfill needed for existing users.
- **Default 50 GB max:** `DEFAULT_MAX_BYTES = 53687091200n` (50 * 1024^3). Stored as a constant in `storage.ts`.
- **Soft delete pattern:** `deletedAt` timestamp on `LockerFile` — row persists for recovery/audit. Phase 9.10 cron will handle permanent cleanup.
- **Floor at zero:** `decrementQuota` prevents negative `usedBytes` (safety against double-delete or stale records).
- **Filesystem fallback preserved:** `getUserStorageBytes()` still exists for potential reconciliation but is not called in the hot path.
