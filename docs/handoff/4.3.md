# Sub-task 4.3 — Review Events (Kind 31337)

## What was built
- **`server/packages/relay/src/routes.ts`** (MODIFIED) — Added two new REST endpoints:
  - `POST /api/games/:slug/reviews` (authenticated) — submit a game review, creates kind 31337 event
  - `GET /api/games/:slug/reviews` (public) — get reviews for a game with aggregation

## Key decisions made during implementation

- **Direct Prisma query for dTag filtering.** The shared `queryEvents()` function doesn't support filtering by `dTag`. Rather than extending the shared interface (which would affect all consumers), the GET endpoint queries `db.event` directly with `kind: KIND_REVIEW, dTag: slug`. This is clean because the `dTag` column is already indexed via the `@@unique([pubkey, kind, dTag])` constraint.

- **Aggregation computed server-side.** `averageRating` and `reviewCount` are computed on every GET request by counting all kind 31337 events with the matching dTag. Since reviews are parameterized replaceable (one per user per game), the total count is bounded by the number of users who reviewed, making this efficient enough without caching.

- **License check uses Prisma's composite unique.** The `@@unique([userId, gameId])` on the License model allows a single `findUnique` call with `userId_gameId` composite key, which is more efficient than a `findFirst` with two conditions.

- **No Zod schema.** Following the pattern from 4.2 (profiles), inline validation is used since the input shape is simple (rating, title, body).

## How it works

### POST /api/games/:slug/reviews (authenticated)
1. Validates `rating` is an integer 1-5 (rejects floats like 3.5)
2. Validates `title` and `body` are non-empty strings
3. Looks up game by slug — 404 if not found
4. Checks license ownership via `License` table — 403 if no ACTIVE license
5. Creates kind 31337 event with `content: JSON.stringify({ rating, title, body })` and `tags: [["d", slug]]`
6. Signs via `signEventForUser`, stores via `storeEvent` (replaceable semantics handle one-review-per-user-per-game)
7. Fans out to WS subscribers, federates outbound
8. Returns `{ eventId, pubkey, rating, title, body, created_at }` with 201 status

### GET /api/games/:slug/reviews (public)
1. Verifies game exists by slug — 404 if not found
2. Queries kind 31337 events with `dTag = slug` via Prisma (supports `limit` and `offset` query params)
3. Computes `averageRating` from all reviews for the game (not just current page)
4. Returns `{ reviews: [...], averageRating, reviewCount, limit, offset }`

### Parameterized replaceable semantics
- Kind 31337 is in the 30000-39999 range, so `storeEvent` automatically handles replaceable behavior
- The d-tag is the game slug, so `pubkey + kind(31337) + dTag(slug)` is the unique key
- Submitting a second review for the same game replaces the first (newer `created_at` wins)

### XSS safety
- Review content is stored as-is in the event's `content` field (JSON-stringified)
- No server-side HTML injection risk because content is always JSON inside a JSON column
- Frontends must escape on render (standard practice)

## Gotchas and surprises

- **Express 5 param types.** `req.params.slug` is typed as `string | string[]` in Express 5, requiring `String(req.params.slug)` to satisfy TypeScript.

- **No `dTag` filter in `EventFilter`.** The shared `queryEvents` doesn't support dTag filtering, so the GET endpoint queries Prisma directly. Future sub-tasks needing dTag filtering should consider extending `EventFilter`.

## How to use / test

### Submit a review
```bash
curl -X POST https://boilerdeck.com/api/games/<slug>/reviews \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"rating": 4, "title": "Great game", "body": "Really enjoyed the gameplay."}'
```

### Get reviews
```bash
curl "https://boilerdeck.com/api/games/<slug>/reviews?limit=10&offset=0"
```

### Verification checks
- Submit review with valid license -> 201, kind 31337 event created
- Submit without license -> 403
- GET returns reviews with rating, title, body, pubkey
- Submit second review -> replaces first (only one event per user per game)
- GET includes averageRating and reviewCount
- Rating outside 1-5 -> 400
- Rating 3.5 (float) -> 400
- POST to nonexistent slug -> 404
- HTML in title/body -> stored safely in JSON
- Two concurrent reviews -> only one survives (replaceable semantics)
