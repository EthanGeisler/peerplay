# Sub-task 5.3 — VPS Seed Box Attestation

## What was built
- **`scripts/seed-attestation-cron.ts`** (NEW) — Standalone script that publishes kind 31338 attestation events for games the VPS Transmission daemon is seeding. Runs via `npx tsx scripts/seed-attestation-cron.ts` on the VPS.

## Key decisions made during implementation

- **Developer pubkey as `p` tag target.** The seed box (signer) attests "I seeded content for developer X." The `p` tag references the game developer's pubkey, not the seed box's own pubkey. This passes the self-attestation check (signer != `p` tag) and is semantically consistent with the Electron client's attestation pattern from 5.2.

- **Direct DB storage, no REST API.** The script runs on the VPS with database access, so it imports `storeEvent` from `@boilerdeck/shared` directly instead of using `POST /api/events` (which would require JWT auth). The stored events are identical to REST-submitted events and pass `verifyEvent()`.

- **`bytesDownloaded` = Transmission's `uploadedEver`.** From the seed box's perspective, upload bytes represent what peers downloaded. The attestation content field is named `bytesDownloaded` to match the standard attestation schema (what the seeder provided to the swarm).

- **Duration = now - addedDate.** Transmission's `addedDate` tracks when the torrent was added, which approximates seeding start time. Duration reflects total seeding time.

- **Developer pubkey lookup via DB chain:** Torrent (infoHash) -> GameVersion (torrentId) -> Game (developerId) -> Developer (userId) -> User (nostrPubkey). Torrents without a developer pubkey are skipped.

## How it works

### Script flow
1. Read `VPS_SEED_PRIVKEY` from env (64-char hex). Derive pubkey via `schnorr.getPublicKey()`.
2. Query Transmission RPC at `http://127.0.0.1:9091/transmission/rpc` (configurable via `TRANSMISSION_RPC_URL`).
   - Performs CSRF dance: first request gets 409 + session ID header, second request uses it.
   - Requests fields: `hashString`, `uploadedEver`, `addedDate`, `name`.
3. Filter to torrents with `uploadedEver > 0`.
4. For each torrent:
   - Look up developer pubkey from DB via infoHash chain.
   - Skip if no developer pubkey or if self-attestation would occur.
   - Create kind 31338 event: `d` tag = infoHash, `p` tag = developer pubkey.
   - Content: `{ infoHash, bytesDownloaded, durationSeconds }`.
   - Sign with `createEvent()`, verify with `verifyEvent()`, store with `storeEvent()`.
5. Log summary: published, skipped, errors.

### Idempotency
Kind 31338 is parameterized replaceable (unique on `pubkey + kind + dTag`). The `dTag` is the infoHash. Running the script twice replaces the attestation with updated upload stats — no duplicates created.

### Attestation event structure
```json
{
  "kind": 31338,
  "pubkey": "<seed-box-pubkey>",
  "content": "{\"infoHash\":\"abc123\",\"bytesDownloaded\":52428800,\"durationSeconds\":86400}",
  "tags": [
    ["d", "abc123"],
    ["p", "<developer-pubkey>"]
  ]
}
```

## Gotchas and surprises

- **Transmission CSRF dance.** The first request to Transmission RPC always returns HTTP 409 with an `X-Transmission-Session-Id` header. The second request must include this header. This is Transmission's built-in CSRF protection, not an error.

- **`storeEvent()` validates before storing.** It calls `verifyEvent()` internally, so the script's own `verifyEvent()` call is a sanity check. If the event signature is wrong, `storeEvent` throws a `ValidationError`.

- **The async attestation validation (`validateAttestationAsync`) is NOT called.** The script stores events directly via `storeEvent()`, which only does signature verification. The async validation (infoHash existence, bytes vs file size) is only wired into the REST and WebSocket paths in `routes.ts`/`ws.ts`. Since the script already validates infoHash existence via the developer pubkey lookup (no torrent = no developer = skip), and the VPS seed box's upload bytes are real Transmission stats, this is acceptable.

- **`VPS_SEED_PRIVKEY` must differ from any developer's privkey.** If the derived pubkey matches a developer's pubkey, that torrent's attestation is skipped (self-attestation). In practice, the VPS seed box should have its own dedicated keypair.

## How to use / test

### Setup on VPS
```bash
# Generate a keypair for the seed box (one-time):
node -e "
  const { schnorr } = require('@noble/curves/secp256k1');
  const privkey = require('crypto').randomBytes(32).toString('hex');
  const pubkey = Buffer.from(schnorr.getPublicKey(privkey)).toString('hex');
  console.log('VPS_SEED_PRIVKEY=' + privkey);
  console.log('Pubkey: ' + pubkey);
"

# Add to VPS environment (e.g., /etc/environment or systemd unit):
export VPS_SEED_PRIVKEY=<generated-privkey>
```

### Manual run
```bash
cd /opt/boilerdeck
VPS_SEED_PRIVKEY=<hex> npx tsx scripts/seed-attestation-cron.ts
```

### Cron setup (e.g., every hour)
```bash
echo "0 * * * * cd /opt/boilerdeck && VPS_SEED_PRIVKEY=<hex> npx tsx scripts/seed-attestation-cron.ts >> /var/log/seed-attestation.log 2>&1" | crontab -
```

### Verify events pass verifyEvent()
```bash
# After running the script, query the DB for attestation events:
npx tsx -e "
  import { db, verifyEvent } from '@boilerdeck/shared';
  const events = await db.event.findMany({ where: { kind: 31338 } });
  for (const e of events) {
    const signed = { id: e.id, pubkey: e.pubkey, created_at: e.createdAt, kind: e.kind, tags: e.tags as string[][], content: e.content, sig: e.sig };
    console.log(e.id.slice(0, 8), verifyEvent(signed) ? 'PASS' : 'FAIL');
  }
  await db.\$disconnect();
"
```

## What the next sub-task needs to know
- **5.4 (Reputation aggregation)** can query kind 31338 events from the event store. VPS seed box attestations will have the seed box's pubkey as `event.pubkey` and the game developer's pubkey in the `p` tag. The seed box pubkey is a unique identity separate from any user — reputation queries should handle both user-generated and seed-box-generated attestations.
- **`VPS_SEED_PRIVKEY`** must be set on the VPS before running the script. The derived pubkey is not stored in the users table — it's a standalone identity.
- The script stores events directly via `storeEvent()` from `@boilerdeck/shared`, not via REST. Events are standard NIP-01 signed events and pass `verifyEvent()`.
