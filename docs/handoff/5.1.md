# Sub-task 5.1 — Attestation Event Kind (31338) Enhanced Validation

## What was built
- **`server/packages/relay/src/kinds.ts`** (MODIFIED) — Enhanced `validateAttestation()` with synchronous checks: self-attestation rejection, future-dated rejection, zero-bytes rejection, bytesDownloaded field requirement. Added `ATTESTATION_FUTURE_LIMIT_SECONDS` exported constant (600 seconds / 10 minutes).
- **`server/packages/relay/src/attestationValidation.ts`** (NEW) — Async validation function `validateAttestationAsync()` that performs DB lookups: unknown infoHash rejection (torrent must exist), bytesDownloaded vs file size validation.
- **`server/packages/relay/src/routes.ts`** (MODIFIED) — Integrated `validateEventKind()` and `validateAttestationAsync()` into both `POST /events` and `POST /events/sign-and-publish` routes, before event storage.
- **`server/packages/relay/src/ws.ts`** (MODIFIED) — Integrated `validateEventKind()` and `validateAttestationAsync()` into WebSocket EVENT handler, after signature verification and before storage.
- **`server/packages/relay/src/index.ts`** (MODIFIED) — Added barrel exports for `validateAttestationAsync` and `ATTESTATION_FUTURE_LIMIT_SECONDS`.

## Key decisions made during implementation

- **Two-layer validation approach.** Synchronous checks stay in `kinds.ts` (self-attestation, future-dated, zero bytes, bytesDownloaded field presence). Async checks that need DB access live in a separate `attestationValidation.ts` module. This keeps `validateEventKind()` synchronous for all kinds while adding the DB-dependent checks in a clean separate function.

- **infoHash is the `d` tag value.** The attestation's `d` tag contains the infoHash, which serves double duty: it's the parameterized replaceable identifier (enabling one attestation per signer+seeder+infoHash) AND the torrent lookup key.

- **File size lives on GameVersion, not Torrent.** The Prisma schema has `fileSizeBytes` on `GameVersion` with a relation to `Torrent` via `torrentId`. The async validation joins through `torrent.version.fileSizeBytes` to get the file size for comparison.

- **Non-attestation events pass async validation immediately.** `validateAttestationAsync()` returns `{ valid: true }` for any event that isn't kind 31338, so callers can always call it without kind-checking.

- **Both REST and WS paths validate.** The validation is wired into `POST /events`, `POST /events/sign-and-publish`, and the WebSocket `EVENT` handler. All three paths reject invalid attestations before storage.

## How it works

### Synchronous validation (kinds.ts → `validateAttestation`)
1. Checks `p` tag exists (seeder pubkey)
2. Checks `d` tag exists (infoHash identifier)
3. **Self-attestation:** `event.pubkey == p tag value` → rejected with "Cannot attest for yourself"
4. **Future-dated:** `event.created_at > now + 600s` → rejected with "Event timestamp too far in the future"
5. Checks content is valid JSON object
6. **bytesDownloaded field:** must be a number, must be > 0. Zero → "No meaningful seeding occurred"

### Async validation (attestationValidation.ts → `validateAttestationAsync`)
1. Extracts infoHash from `d` tag
2. Looks up `db.torrent.findFirst({ where: { infoHash } })` with joined `version.fileSizeBytes`
3. **Unknown infoHash:** no torrent found → rejected with "Unknown infoHash"
4. **Bytes exceeded:** `bytesDownloaded > fileSizeBytes` → rejected with "bytesDownloaded exceeds torrent file size"

### Parameterized replaceable semantics
One attestation per (signer, seeder, infoHash) is handled by the existing `d` tag + replaceable event semantics in `storeEvent()`. The `d` tag contains the infoHash, and the unique constraint `[pubkey, kind, dTag]` on the events table ensures only one event per signer per infoHash. The `p` tag (seeder) is part of the event content/tags but doesn't need a separate DB constraint because the `d` tag already scopes the attestation.

### Integration points
```typescript
// In routes.ts POST /events and POST /events/sign-and-publish:
const kindResult = validateEventKind(event);
if (!kindResult.valid) throw new ValidationError(kindResult.error!);

const asyncResult = await validateAttestationAsync(event);
if (!asyncResult.valid) throw new ValidationError(asyncResult.error!);

// In ws.ts handleEvent:
const kindResult = validateEventKind(event);
if (!kindResult.valid) { sendOk(ws, event.id, false, `invalid: ${kindResult.error}`); return; }

const asyncResult = await validateAttestationAsync(event);
if (!asyncResult.valid) { sendOk(ws, event.id, false, `invalid: ${asyncResult.error}`); return; }
```

## Gotchas and surprises

- **No `sizeBytes` on Torrent model.** The task description mentioned `Torrent.sizeBytes` but the actual schema has `fileSizeBytes` on `GameVersion`, related to Torrent via `torrentId`. The async validation joins through `torrent.version.fileSizeBytes`.

- **BigInt comparison.** `fileSizeBytes` is a `BigInt` in Prisma. We convert to `Number()` for comparison with `bytesDownloaded`. This is safe for files up to ~9 PB (Number.MAX_SAFE_INTEGER).

- **File size of 0 skips bytes check.** If the torrent's associated GameVersion has `fileSizeBytes: 0` (default), the bytes-exceeded check is skipped. This avoids false rejections for torrents that were created before file size tracking.

## How to use / test

### Submit a valid attestation (should succeed)
```bash
# Via sign-and-publish (requires auth + valid signing key in Redis):
curl -X POST https://boilerdeck.com/api/events/sign-and-publish \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "kind": 31338,
    "tags": [["p", "<seeder-pubkey>"], ["d", "<valid-infoHash>"]],
    "content": "{\"bytesDownloaded\": 1024000}"
  }'
```

### Self-attestation (should fail 400)
Set the `p` tag pubkey to your own pubkey.

### Unknown infoHash (should fail 400)
Use a `d` tag value that doesn't match any torrent's `infoHash`.

### Zero bytes (should fail 400)
Set `bytesDownloaded: 0` in content.

### Bytes exceeded (should fail 400)
Set `bytesDownloaded` to a value larger than the torrent's file size.

### Future-dated (should fail 400)
Set `created_at` to more than 10 minutes in the future.
