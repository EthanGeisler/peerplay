# 8.13 — Signed Listing Publishing Flow (End-to-End)

## Summary

Implemented end-to-end Schnorr signature flow for listings: creation sets `creatorPublicKey`, publishing generates a signature, and signed listings are federated to external relays. Client-side local signing is also supported as a secondary path.

## What Changed

### Server: Catalog Service (`server/packages/catalog/src/service.ts`)
- `createListing()` now accepts optional `creatorPublicKey` parameter — set from the developer's `user.nostrPubkey`
- `publishListing()` now accepts optional `userId` parameter, used to:
  - Set `creatorPublicKey` on the listing if not already set
  - Generate a Schnorr signature over canonical listing data using the user's Redis-cached signing key
- Added `signListingData()` internal function that:
  - Loads the user's cached signing key from Redis (`signing_key:{userId}`)
  - Decrypts it using `SIGNING_CACHE_KEY` env var (AES-256-GCM)
  - Signs `JSON.stringify({ title, slug, description, priceCents, contentType })` via SHA-256 + Schnorr

### Server: Catalog Routes (`server/packages/catalog/src/routes.ts`)
- `POST /developer/listings` and `POST /developer/games` — look up `user.nostrPubkey` and pass to `createListing()`
- `PATCH /developer/listings/:id/publish` and `PATCH /developer/games/:id/publish` — pass `req.user.sub` (userId) to `publishListing()` for signing
- Both publish routes now call `federateListingOutbound()` after publish if the listing has both `creatorPublicKey` and `signature`

### Server: Federation (`server/packages/relay/src/federation.ts`)
- Added `federateListingOutbound()` — POSTs signed listing data to all connected external relays' `POST /api/relay/listings` endpoint
- Non-blocking: uses fire-and-forget fetch with 15s timeout, errors are logged but don't propagate

### Client: IPC + Preload
- Added `listings:sign` IPC handler in `client/src/main/index.ts` — signs listing data locally using keyManager's stored private key
- Updated `client/src/main/preload.ts` — exposed `window.boilerdeck.listings.sign()`
- Updated `client/src/renderer/env.d.ts` — added type declarations for `listings.sign()`

### Client: DevGameDetail (`client/src/renderer/pages/developer/DevGameDetail.tsx`)
- After a successful publish API call, if the user has a local key (`window.boilerdeck.crypto.hasKey()`):
  - Signs the listing locally via `window.boilerdeck.listings.sign()`
  - Submits the signed listing to the relay via `POST /api/relay/listings`
- This is a secondary path — server-side signing is the primary path
- All local signing is wrapped in try/catch — failures are logged but don't block the publish

### Types (`client/src/renderer/types.ts`)
- Added optional `contentType` field to `DevGameData` interface

## Canonical Signed Data Format

```typescript
const canonical = JSON.stringify({ title, slug, description, priceCents, contentType });
const messageBytes = new TextEncoder().encode(canonical);
const messageHash = sha256(messageBytes);
const signature = schnorr.sign(messageHash, privateKey);
```

This matches the format used by `POST /api/relay/listings` (8.3) and the federation listing import verification (8.5).

## Important Notes

- **Signing is always non-fatal.** If signing fails (no cached key, self-custody user, key decryption failure), the listing is still published — just without a signature.
- **Self-custody users** (`custodyMode === "SELF_CUSTODY"`) skip server-side signing. They can sign locally via the Electron client.
- **`creatorPublicKey`** is set at creation time and backfilled on first publish if missing.
- **Federation** only happens when both `creatorPublicKey` and `signature` are present on the listing.
- **Pre-existing listings** without signatures continue to work — the fields are nullable.
