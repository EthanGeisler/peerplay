# Sub-task 4.6 — Follow List Events (Kind 3)

## What was built
- **`server/packages/relay/src/routes.ts`** (MODIFIED) — Added three new REST endpoints for follow list management:
  - `POST /api/follows` (authenticated) — follow a user
  - `GET /api/follows/:pubkey` (public) — get a user's follow list
  - `DELETE /api/follows/:pubkey` (authenticated) — unfollow a user

## Key decisions made during implementation

- **Followed the profile route pattern exactly.** The follow endpoints use the same `signEventForUser` + `storeEvent` + `fanOutEvent` + `federateOutbound` flow established in 4.2.

- **Kind 3 is regular replaceable (not parameterized).** The `isRegularReplaceableKind` function from shared/events.ts already recognizes kind 3, and `normalizeDTag` returns `""` for it. This means the eventStore automatically handles replacement — only one kind 3 event per pubkey exists at a time. No additional work needed.

- **Atomic follow/unfollow.** Each follow or unfollow operation loads the existing kind 3 event, rebuilds the full tag array with the change applied, and creates a complete new event. This is atomic from the event perspective — the new event fully replaces the old one.

- **Empty list returns `{ follows: [] }`, not 404.** The GET endpoint returns an empty array if no kind 3 event exists for the pubkey, as specified.

- **Case-insensitive pubkey comparison.** All pubkey comparisons use `.toLowerCase()` to prevent duplicate follows due to case differences.

- **Self-follow prevention.** POST /follows rejects attempts to follow your own pubkey with a 400 validation error.

- **Content is empty string.** Per the spec, we use `""` for content (no relay hints for now). This is valid per NIP-02.

- **No Zod schema.** The input is a single `pubkey` field with inline validation, matching the lightweight pattern used by profiles.

## How it works

### POST /api/follows (authenticated)
1. Validates `pubkey` from request body (64-char hex)
2. Loads authenticated user's `nostrPubkey` from DB
3. Prevents self-follow
4. Queries existing kind 3 event for this user
5. Extracts existing `["p", ...]` tags, adds new target if not already present
6. Signs new kind 3 event via `signEventForUser`
7. Stores via `storeEvent` (replaceable — replaces existing kind 3)
8. Fans out to WS subscribers, federates outbound
9. Returns `{ follows: ["pubkey1", "pubkey2", ...] }`

### GET /api/follows/:pubkey (public, no auth)
1. Validates pubkey param (64-char hex)
2. Queries latest kind 3 event for that pubkey
3. Returns `{ follows: [] }` if no event exists
4. Extracts `["p", ...]` tags and returns `{ follows: ["pubkey1", ...] }`

### DELETE /api/follows/:pubkey (authenticated)
1. Validates target pubkey param (64-char hex)
2. Loads authenticated user's `nostrPubkey` from DB
3. Queries existing kind 3 event for this user
4. Filters out the target pubkey from `["p", ...]` tags
5. Signs new kind 3 event with remaining tags
6. Stores (replaces old), fans out, federates
7. Returns `{ follows: ["remaining1", ...] }`

## Gotchas and surprises
- None. The replaceable event infrastructure from 4.2 handled kind 3 seamlessly.

## How to use / test

### Follow a user
```bash
curl -X POST https://boilerdeck.com/api/follows \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"pubkey":"<64-char-hex-pubkey-to-follow>"}'
```
Response: `{"follows":["<pubkey1>","<pubkey2>"]}`

### Get follow list
```bash
curl https://boilerdeck.com/api/follows/<64-char-hex-pubkey>
```
Response: `{"follows":["<pubkey1>","<pubkey2>"]}` or `{"follows":[]}`

### Unfollow a user
```bash
curl -X DELETE https://boilerdeck.com/api/follows/<64-char-hex-pubkey-to-unfollow> \
  -H "Authorization: Bearer <access_token>"
```
Response: `{"follows":["<remaining-pubkeys>"]}`

### Verify replaceable semantics
Follow two users, then query the events table:
```bash
curl "https://boilerdeck.com/api/events?kinds=3&authors=<your-pubkey>"
```
Should return exactly one event with both `["p", ...]` tags.

## What the next sub-task needs to know
- **4.7 (User profile page)** will need to call `GET /api/follows/:pubkey` to show the follow/unfollow button state and follow count.
- **The response shape is `{ follows: string[] }`** — an array of 64-char hex pubkeys.
- **Follow count** can be derived from `follows.length` on the response.
- **Follower count** (who follows a given user) is not implemented — would require querying all kind 3 events containing a `["p", targetPubkey]` tag. This could be added as a future enhancement or computed client-side via relay subscription.
