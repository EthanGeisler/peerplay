# Sub-task 3.5 — Keypair Generation on Registration + Key Management

## What was built
- **`server/packages/relay/src/routes.ts`** (MODIFIED) — Added two new REST endpoints:
  - `GET /api/relay/me/keys` — export pubkey + privkey (authenticated, custodial returns both, self-custody returns pubkey only)
  - `POST /api/relay/me/import-key` — import a private key, derive and update pubkey, switch to self-custody

## Key decisions made during implementation
- **Key export from Redis cache, not DB.** The privkey for custodial users lives in Redis (encrypted with `SIGNING_CACHE_KEY`), not in the DB (which has the password-encrypted version). Using the Redis cache avoids needing the user's password. If the cache has expired, the user must log in again.
- **Self-custody users get pubkey only.** `GET /relay/me/keys` returns `{ pubkey, privkey: null }` for self-custody users since the server doesn't hold their private key.
- **Import switches to self-custody.** Importing a key clears `encryptedNsec` and `encryptedMnemonic` from DB, sets `custodyMode: "SELF_CUSTODY"`. The imported key is still cached in Redis for server-side signing convenience.
- **Cache helpers duplicated from auth service.** The `decryptFromCache` and `encryptForCache` functions match the exact format used in `auth/src/service.ts` and `auth/src/signing.ts` (nonce:tag:ciphertext, AES-256-GCM). This duplication is acceptable — extracting to shared would require a larger refactor.

## How it works

### GET /relay/me/keys
1. Authenticate user via JWT
2. Load user from DB (pubkey, custodyMode)
3. If self-custody → return `{ pubkey, privkey: null }`
4. If custodial → load encrypted signing key from Redis (`signing_key:{userId}`)
5. Decrypt with `SIGNING_CACHE_KEY` env var
6. Return `{ pubkey, privkey }` both as hex strings

### POST /relay/me/import-key
1. Authenticate user via JWT
2. Validate `privkey` is 64-char hex (32 bytes)
3. Derive pubkey from privkey using `schnorr.getPublicKey()`
4. Update user in DB: set new pubkey, clear encrypted keys, set SELF_CUSTODY
5. Cache the imported key in Redis (encrypted) for server-side signing
6. Return `{ pubkey }` (the derived pubkey)

## Gotchas and surprises
- The `@noble/curves/secp256k1.js` import for `schnorr` was added directly to routes.ts. This is fine since the relay package already depends on `@boilerdeck/auth` which brings in `@noble/curves`.
- Redis cache format is `nonce:tag:ciphertext` (3 colon-separated hex parts), NOT the `v1:salt:nonce:tag:ciphertext` format used for password-encrypted DB values. Don't confuse the two.

## How to use / test
```bash
# Login first to cache signing key
curl -X POST https://boilerdeck.com/api/auth/login -H "Content-Type: application/json" -d '{"email":"test@test.com","password":"password"}'

# Export keys (use accessToken from login response)
curl https://boilerdeck.com/api/relay/me/keys -H "Authorization: Bearer <token>"
# → { "pubkey": "abc123...", "privkey": "def456..." }

# Import a key
curl -X POST https://boilerdeck.com/api/relay/me/import-key -H "Authorization: Bearer <token>" -H "Content-Type: application/json" -d '{"privkey":"<64-char-hex>"}'
# → { "pubkey": "<derived-pubkey>" }
```
